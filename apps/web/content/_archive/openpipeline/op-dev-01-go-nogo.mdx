## 빌더는 끝났는데, 엔진이 아까웠다

[워크플로우 빌더 8부작](/series/workflow-builder)을 만들며 계속 마음에 걸리는 사실이 하나 있었다. 이 엔진, 생각보다 범용적이라는 것.

빌더의 심장은 NodeSpec 계약이다. zod 입출력 스키마와 handler 하나로 노드 한 종류가 정의되고 레지스트리에 등록하면 팔레트부터 실행, 검증까지 전부 따라온다([1편 참고](/posts/flow-ai/wf-dev-01-architecture)). 그리고 이 계약에는 Flow AI 냄새가 없다. 실행기가 올라탄 LangGraph는 저수준 오케스트레이션 런타임이라 도메인을 모르고 런타임 의존성은 zod, LangGraph, MCP SDK처럼 전부 공개 스택이다. 사용자가 그린 DAG를 zod 계약으로 검증하며 실행하고 MCP 도구를 노드로 바로 꽂을 수 있는 엔진. 이 조합을 갖춘 오픈소스는 의외로 드물다. 꺼내서 npm에 올리면 사내 제품 바깥에서도 쓸 수 있는 물건이 되겠다는 생각이 들었다.

하지만 "추상이 깨끗하다"는 인상과 "밖에서 돈다"는 사실 사이에는 큰 강이 있다. 그래서 검토의 원칙을 하나로 정했다. **추론 금지, 실측만.**

## 희망 대신 실측

검토 방식은 이랬다. 코드를 직접 열어 결합 지점을 전수 조사하고 개발 과정에서 쌓인 설계 노트 39개와 코드가 아직 일치하는지 교차 확인했다. 대상 규모는 워크플로우 모듈 약 8.7K LOC, MCP 모듈 약 4.5K LOC, 공유 계약 약 1.1K LOC.

첫 발견은 뼈아팠다. 39개 노트와 모든 설계 결정 기록 어디에도 **오픈소스화를 다룬 문서가 없었다.** 설계는 일관되게 정확성과 제품 통합을 최우선으로 했고 임의 노드를 등록할 수 있는 확장성은 그 부산물이었다. 즉 이 작업은 처음부터 의도된 분리가 아니라 사후 추출이다. 사후 추출은 항상 예상보다 비싸다.

실측이 찾아낸 결합 지점은 이렇다.

| 결합 지점 | 실태 | 추출 난이도 |
| --- | --- | --- |
| 모노레포 공유 패키지 | 40여 곳 import, 대부분 타입과 zod 스키마 | 낮음 |
| Prisma 영속화 | 워크플로우, 노드, 엣지, 실행, 실행 스텝 5개 모델이 1,700줄대 거대 스키마에 동거 | 중간 |
| NestJS DI | 엔진 전체가 프레임워크 데코레이터에 종속 | 중간 |
| 사내 도구 노드 | 협업 데이터 조회, 웹 검색 노드가 사내 도구 구현을 직접 import. 단 IF, LLM, MCP 노드는 무관 | 낮음 |
| MCP 카탈로그 | 사내 OAuth 토큰 저장소, 회사별 도구 allowlist에 결합 | **높음** |
| 프론트 빌더 | 캔버스는 깨끗하나 바깥 껍데기가 인증, 기능 플래그, 한국어 하드코딩 79곳에 결합 | 중간 |

진짜 장벽은 마지막에서 두 번째 줄이다. MCP 카탈로그 서비스는 어떤 회사의 어떤 사용자가 어떤 도구를 쓸 수 있는지를 3단 권한(시스템 관리자의 provider 등록, 회사 관리자의 활성화, 사용자의 개인 연동)으로 풀어낸다. 사내 제품에는 꼭 필요한 구조지만 오픈소스 사용자에게 "워크플로우 하나 돌리려면 회사와 관리자와 승인 체계를 먼저 세팅하라"고 요구할 수는 없다. 이 멀티테넌시와 인증 결합을 들어내지 않으면, 공개하는 순간 사내 인증 모델이 그대로 노출되기도 한다.

1차 판정에 적대적 검증을 한 번 더 돌렸는데, 여기서 낙관 두 건이 깨졌다. "공유 패키지 결합은 거의 다 타입이다"는 틀렸다. 상태 경로 검증 함수와 비용 초기화 상수 같은 런타임 로직이 섞여 있어서 타입으로 오분류해 걷어내면 조용히 깨진다. "실행 오케스트레이터는 인터페이스 주입만으로 프레임워크 없이 돈다"도 틀렸다. 프레임워크 생명주기 훅과 예외 타입, 리포지토리 세 개가 critical path에 박혀 있어 추출이 아니라 약 400 LOC 재작성이 정답이었다. 대신 비관 한 건도 깨졌다. 멀티테넌시는 하드 블로커가 아니었다. 도구 로딩 경로 자체는 테넌시를 모르는 코드라, 환경변수 기반 서버 목록으로 DB를 안 타고 우회할 수 있었다.

## 판정은 조건부 GO

정리하면 판정은 두 줄이다.

**현 레포 그대로 공개는 NO-GO.** 사내 인증 모델과 회사별 설정, 사내 도구가 노출되고 애초에 모노레포 밖에서는 빌드조차 안 된다.

**헤드리스 코어 추출은 GO. 단, 조건부.** 조건은 경계선을 긋고 바깥의 것들을 버릴 수 있느냐다.

- **남기는 것**: NodeSpec 계약, 레지스트리, LangGraph 컴파일러, MCP 리졸버, 그리고 도메인 무관 노드(IF, LLM, MCP).
- **버리는 것**: 멀티테넌시(회사 ID, 권한 스코프), 사내 전용 노드, 셀프 스케줄링, NestJS와 Prisma 하드 의존.
- **역전시키는 것**: 3단 권한은 삭제가 아니라 CatalogPolicy라는 선택적 인터페이스로 뒤집는다. provider 필터링, 도구 allowlist, 토큰 해석을 hook 세 개로 열어 두면, 개인 사용자는 정책 없이(전부 허용, env 토큰) 바로 쓰고 엔터프라이즈는 자기 권한 모델을 hook 뒤에 끼운다.

이 경계선이 이번 시리즈 전체의 뼈대다. 오픈소스화는 코드를 복사하는 일이 아니라, 무엇이 도메인이고 무엇이 엔진인지를 칼로 가르는 일이었다.

## 계획: P0에서 P5까지

경계선을 실행 계획으로 옮기면 여섯 단계가 된다.

- **P0**: 공유 패키지에서 코어 조각 분리. 타입, 스키마, 런타임 유틸을 골라내 core가 langgraph, langchain, zod만으로 빌드되게 한다.
- **P1**: 순수 커널 추출. 컴파일러와 노드 러너를 plain class로 바꾸고 IF, LLM 노드를 얹어 프레임워크 0으로 DAG를 돌린다.
- **P2**: 오케스트레이터 재작성과 인메모리 스토어. DB 없이 15줄 스크립트로 엔진이 돌면 통과.
- **P3**: 어댑터 층. MCP 로더, Prisma 스토어, HTTP와 SSE 서버를 선택적 패키지로 붙인다.
- **P4**: React 빌더를 controlled 컴포넌트 라이브러리로 분리하고 Vite 플레이그라운드로 검증한다.
- **P5**: npm 하드닝과 publish. peerDeps 핀, ESM/CJS 듀얼 빌드, 외부 설치 스모크까지.

결과물은 core, runtime, nodes, mcp, store-memory, store-prisma, server, react의 8개 패키지다. 지금은 [OpenPipeline](https://github.com/carefreelife98/openpipeline)이라는 이름으로 npm에 올라가 있다. 계획 단계의 이름은 사실 이게 아니었는데, 그 이름이 왜 바뀌었는지는 2편에서 만난다.

판정은 GO였다. 조건부로. 경계선 바깥의 것들을 버릴 수 있다면. 다음 편은 여덟 패키지를 하루에 뽑아낸 P0부터 P5까지의 기록이다.
