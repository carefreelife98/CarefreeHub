## 파이프라인이 돌아가자 다른 문제가 자라기 시작했다

1편에서 쓴 대로, Assistant V2 파이프라인은 잘 굴러갔다. 분석 → 검색 → 검증 → 재시도의 흐름이 상태 머신으로 명시되어 있었고, 어디서 무엇이 실패했는지 로그로 추적할 수 있었다. 그런데 서비스가 성장하는 방향은 파이프라인의 안쪽이 아니라 바깥쪽이었다. 어시스턴트 옆에는 일반 채팅이 있었고, 일반 채팅에는 웹 검색, 이미지 생성, 코드 생성, 파일 파싱 같은 기능이 분기마다 하나씩 추가됐다.

문제는 그 기능들이 전부 **시스템 프롬프트로만 정의되고 있었다는** 점이다. 새 기능이 붙을 때마다 "이런 요청이 오면 이 도구를 이렇게 써라"는 규칙이 하나의 프롬프트에 문단으로 쌓였다. 코드는 도구를 등록할 뿐이고, 언제 어떻게 쓰는지는 전부 프롬프트의 몫. 2025년 가을쯤, 그 프롬프트는 더 이상 사람이 한 호흡에 읽을 수 없는 크기가 되어 있었다.

## 증상: 버그인데 고칠 코드가 없다

당시 노트에 적어둔 증상들을 그대로 옮기면 이렇다.

- **코드가 코드블록 없이 응답된다.** 마크다운 펜스가 빠진 채 코드가 평문으로 흘러나오면 프론트 렌더링이 깨지고, 사용자가 화면을 조작하다 오류를 만난다.
- **이미지 생성이 문맥을 타지 않는다.** "이미지 만들어줘"라고 정확히 명령해야만 동작하고, 대화 흐름상 명백히 이미지가 필요한 상황에서는 반응하지 않는다.
- **기본적인 마크다운 규칙이 흔들린다.** 표가 깨지고, 리스트 들여쓰기가 무너지고, 어제 멀쩡하던 포맷이 오늘 어긋난다.

하나하나는 사소해 보이지만, 이 버그들의 공통점이 심각했다. **고칠 코드가 없다.** 코드블록 누락은 어느 함수의 버그가 아니다. 재현 조건도 불명확하고, 스택 트레이스도 없다. 할 수 있는 일은 시스템 프롬프트에 "코드는 반드시 코드블록으로 감싸라"는 문장을 한 줄 더 얹는 것뿐이었다. 그 수정으로 해결됐는지 검증할 방법도 없고, 다음 기능이 추가되어 프롬프트가 더 길어지면 언제든 재발할 수 있었다. 프롬프트 수정만이 유일한 해결책인 상태. 이건 유지보수가 아니라 기우제에 가까웠다.

원인 자체는 알려진 현상이었다. 프롬프트가 길어질수록 모델이 개별 규칙을 지키는 밀도는 떨어진다. 웹 검색 규칙, 이미지 생성 규칙, 코드 포맷 규칙, 마크다운 규칙이 한 컨텍스트에서 경합하면 무엇 하나 확실하게 지켜지지 않는다. 규칙을 더 얹는 방식은 문제를 키우는 방향이었다.

## 진단: 프롬프트 비대화는 구조의 증상이었다

프롬프트만 문제였다면 프롬프트를 다듬으면 된다. 하지만 코드를 열어보니 프롬프트 비대화는 결과였고, 원인은 구조에 있었다.

**첫째, 일반 채팅은 이중 추상화 위에 있었다.** 일반 채팅은 LangGraph 워크플로(시작 → 보안 마스킹 → 메시지 생성 → 응답 생성 → 제목 생성 → 완료)로 감싸여 있었는데, 정작 응답 생성 노드 안에서 다시 LangChain 에이전트를 생성해 돌리고 있었다. 그래프 위에 에이전트가 중첩된 구조. 체크포인트와 인터럽트, 스트리밍 세션 관리까지 그래프 계층에 붙어 있었지만, 일반 채팅의 본질은 "단일 에이전트 호출 + 스트리밍"이라 그 대부분이 오버헤드였다. 그리고 그 에이전트 하나에 모든 도구가 바인딩되어 있었으니, 프롬프트가 모든 도구의 사용법을 설명해야 했던 것이다.

**둘째, 어시스턴트는 완전히 다른 세계에 있었다.** V2에서 만든 어시스턴트 그래프는 노드 다섯 개에 파이프라인 전용 중첩 상태를 갖고 있었고, 분석용 LLM·실행용 LLM·검증용 LLM이 각각 분리되어 있었다. 그 자체로는 동작했지만, 일반 채팅과 어시스턴트가 **거의 같은 일(프롬프트 조립, 도구 호출, 스트리밍, 메시지 저장)을 하면서 코드를 한 줄도 공유하지 않았다.** 웹 검색 처리 로직이 두 벌, 스트림 이벤트 변환이 두 벌, 저장 로직이 두 벌. 한쪽에서 고친 버그가 다른 쪽에 그대로 남아 있는 일이 반복됐다.

정리하면 이렇다. 기능 규칙이 프롬프트에만 존재하는 것, 단순한 도메인이 과한 추상화를 쓰는 것, 비슷한 두 도메인이 코드를 공유하지 않는 것. 셋은 별개의 문제처럼 보였지만 답은 하나로 수렴했다. **채팅 도메인을 하나의 에이전트 모듈로 공통화하고, 비대한 프롬프트를 역할별 에이전트로 쪼갠다.** 마침 LangChain/LangGraph가 v1 메이저 버전으로 올라가면서 에이전트 구성 API와 미들웨어 체계가 정리된 시점이라, 업그레이드와 재설계를 한 번에 진행하기로 했다.

## 재설계: 세 가지 결정

### 결정 1. 일반 채팅에서 LangGraph를 걷어낸다

가장 먼저 한 일은 덜어내기였다. 일반 채팅 경로에서 그래프, 체크포인트, 인터럽트를 전부 제거하고, 컨트롤러 → 서비스 → 에이전트 호출로 이어지는 단일 경로로 재구성했다. 유저 메시지 저장, 대화 컨텍스트 로딩, 파일 컨텍스트 생성 같은 전처리는 서비스 계층의 평범한 코드가 됐고, 그래프에서만 가능했던 보안 마스킹 확인은 별도 REST 경로로 빠졌다.

1편에서 "자율성이 필요한 곳과 결정성이 필요한 곳을 구분한다"고 썼는데, 이번에 그 기준이 하나 더 생겼다. **상태 분기가 없는 흐름에 상태 그래프를 쓰지 않는다.** 그래프는 분기와 재시도가 있는 곳에서만 값을 하고, 직선 흐름에서는 비용만 남는다.

### 결정 2. 프롬프트를 쪼개는 대신 에이전트를 쪼갠다

핵심 결정. 비대한 프롬프트를 문단 단위로 정리하는 게 아니라, 기능 단위로 **서브에이전트를** 분리했다. 웹 검색, 이미지 생성, 코드 작성, Flow 데이터 검색. 각 서브에이전트는 자기 도구와 자기 시스템 프롬프트만 가진다. 메인 에이전트의 프롬프트에는 대화 규칙과 "어떤 작업을 누구에게 위임할지"에 대한 오케스트레이션 지침만 남는다.

```typescript
// 서브에이전트: 도구도 프롬프트도 자기 역할 것만 가진다
const webSearcher: SubAgent = {
  name: "web_searcher",
  systemPrompt: webSearcherPrompt(), // 웹 검색 규칙"만" 담긴 프롬프트
  tools: [webSearchTool],
  middleware: [toolCallLimitMiddleware({ runLimit: 3, toolName: "web_search" })],
};

// 메인 에이전트: 오케스트레이션 규칙만 남은 얇은 프롬프트
const agent = createAgent({
  model: userSelectedModel, // 응답 톤·표현은 사용자가 고른 모델이
  systemPrompt: mainSystemPrompt,
  middleware: [
    modelCallLimitMiddleware({ runLimit: 3, exitBehavior: "end" }),
    todoListMiddleware({ systemPrompt: "작업 시작 전 todo를 만들고 전부 완료하라." }),
    subAgentMiddleware({ defaultModel: reasoningModel, subagents }), // 위임은 서브에이전트가
  ],
});
```

이 구조가 프롬프트 비대화 증상을 어떻게 해소하는지가 중요하다. 코드블록 규칙은 이제 프로그래머 서브에이전트의 프롬프트에만 존재하고, 그 프롬프트는 짧아서 잘 지켜진다. 이미지 생성 판단은 "프롬프트 속 한 문단"이 아니라 "이 작업을 이미지 생성 에이전트에 위임할까"라는 메인 에이전트의 라우팅 결정이 되어, 문맥 기반으로 동작한다. 각 호출의 컨텍스트가 격리되니 규칙끼리 경합하며 서로를 오염시키는 일도 줄었다.

![이미지 생성 서브에이전트 동작 화면](/images/portfolio/flow-ai/flowai-agent-chat-sample-2.png)
_조사와 이미지 생성이 한 요청에 섞여 있어도, 메인 에이전트가 문맥으로 판단해 이미지 생성 서브에이전트에 위임한다._

모델 배치도 역할을 따랐다. 서브에이전트들은 스트리밍을 끈 고성능 추론 모델을 공유해 리서치·분석·생성을 담당하고, 메인 에이전트는 사용자가 선택한 모델로 최종 응답의 톤과 표현을 맡는다. 대신 호출 횟수는 늘어날 수 있어서, 모델 호출과 도구 호출에 상한 미들웨어를 걸어 비용의 위 뚜껑을 닫아뒀다.

### 결정 3. 어시스턴트는 그래프를 줄이고 에이전트를 재사용한다

어시스턴트에서는 그래프를 없애는 대신 **그래프의 책임을 줄였다.** 다섯 노드짜리 파이프라인을 요청 분석 → RAG → 응답의 3노드로 축소하고, 중첩 상태를 필수 필드만 남긴 평평한 상태로 재정의했다. 분석 노드는 경량 모델의 구조화 출력 한 번으로 검색 필요 여부와 벡터 검색 질의를 뽑아내고, 별도 노드였던 검증·재시도는 RAG 노드 내부의 재귀 횟수 제한으로 흡수했다.

그리고 마지막 응답 노드가 일반 채팅과 **같은 에이전트 + 서브에이전트 구조를 그대로 재사용한다.** 어시스턴트만의 것(RAG, 연결 지식 분석)은 그래프가 오케스트레이션하고, 응답 생성이라는 공통 관심사는 공통 모듈이 처리한다. 스트림 이벤트를 SSE로 변환하는 핸들러, 텍스트·검색 링크·생성 이미지·서브에이전트 결과를 저장하는 영속화 로직도 두 도메인이 한 벌을 공유하게 됐다. "웹 검색 버그를 두 군데서 고치는" 일이 구조적으로 사라진 것이다.

공통화가 자리 잡자 후속 정리도 따라왔다. 기능 활성화 여부를 판단하는 로직(권한 플래그, 채팅 설정, 관리자 차단, 사용자 토글)이 에이전트마다 흩어져 있던 것을, "이 요청에서 어떤 기능이 켜져 있고(enabled) 무엇이 명시적으로 요청됐는지(forced)"를 한 번에 계산하는 단일 서비스로 모았다. 프롬프트에서 규칙을 꺼냈듯, 설정 판단도 코드의 한 곳으로 모은 셈이다.

## 배운 것, 그리고 예고

부수 효과도 있었다. 서브에이전트의 작업 스트림이 독립된 구조로 저장되고 화면에 표시되면서, 사용자가 "지금 에이전트가 무슨 일을 하는지"를 볼 수 있게 됐다. 프롬프트 속에 숨어 있던 동작이 관찰 가능한 단위로 바뀐 것인데, 이 가시성 문제는 나중에 따로 한 편을 쓸 만큼 커진다.

이 시기를 지나며 남은 원칙은 세 가지다.

1. **프롬프트는 기능의 저장소가 아니다.** 규칙이 코드로 표현될 수 있다면 코드로, 에이전트 분리로 표현될 수 있다면 분리로 옮긴다. 프롬프트에는 짧게 유지될 수 있는 것만 남긴다.
2. **추상화는 도메인의 복잡도에 비례해야 한다.** 직선 흐름에 상태 그래프를 씌우는 것도, 분기 있는 흐름을 프롬프트로 때우는 것도 같은 종류의 실수다.
3. **같은 일을 하는 코드가 두 벌이면, 버그도 두 벌이다.** 공통화의 가치는 코드량 감소가 아니라 수정 지점의 단일화에 있다.

다만 이 그림에는 아직 말하지 않은 부분이 있다. 서브에이전트 위임 구조를 만들면서 우리는 LangChain의 에이전트 하네스 라이브러리인 **deepagents에** 꽤 깊이 올라탔는데, 이 하네스는 문서가 약속한 대로만 움직여주지 않았다. 간단한 인사에도 서브에이전트를 불러 거창한 작업 계획부터 세우고, "랜딩 페이지 만들어줘"라는 요청에는 화면에 보여주는 대신 파일시스템 도구로 서버 로컬에 저장해버리고, 웹 검색은 한 번이면 될 것을 다섯 번 넘게 반복했다. 서브에이전트의 응답이 부모 에이전트의 tool 인자 스트림에 실려 도착하는 바람에 스트리밍 파싱이 통째로 깨진 것은 덤이다. 결국 미들웨어로 하나씩 고삐를 채워야 했던 이야기. 다음 편은 그 씨름의 기록이다.
