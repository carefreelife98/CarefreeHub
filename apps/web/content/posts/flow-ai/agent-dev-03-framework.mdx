## 프레임워크에 올라탄 이유

2편에서 쓴 대로, 우리는 비대한 프롬프트를 역할별 서브에이전트로 쪼개면서 한 에이전트 프레임워크에 꽤 깊이 올라탔다. LangChain v1과 호환되는, 서브에이전트 위임과 작업 계획 수립을 기본으로 제공하는 프레임워크였다.

2025년 11월의 검토 노트를 다시 보면, 공식 문서가 말하는 적합 조건과 우리 상황이 깔끔하게 맞아떨어졌다. 복잡한 다단계 작업을 계획을 세워 수행해야 할 때 — 일반 채팅은 웹 검색, 이미지 생성, 코드 생성, 파일 파싱을 문맥에 맞게 조합해야 했다. 특화 에이전트에게 작업을 위임해 컨텍스트를 격리해야 할 때 — 이건 정확히 우리가 프롬프트 비대화를 해결하려던 방식이었다. 직접 위임 루프를 만드는 대신 검증된 구현 위에서 시작하면 시간을 벌 수 있다고 판단했고, 실제로 서브에이전트 구조 자체는 빠르게 섰다.

문제는 그다음이었다. 프레임워크는 "잘 동작하는 기본값"을 잔뜩 들고 왔는데, 그 기본값들은 우리 서비스가 **협업툴 안의 채팅**이라는 사실을 전혀 몰랐다. 문서가 약속한 대로가 아니라 기본값이 설계된 대로 움직이는 프레임워크와, 네 판의 씨름이 시작됐다.

## 1라운드 — 생각이 너무 많다

첫 증상은 도입 직후에 나왔다. 간단한 인사말을 던져도 에이전트가 기본 제공되는 범용(general-purpose) 서브에이전트를 호출해 거창한 작업 계획부터 세웠다. "안녕하세요"에 todo 리스트가 만들어지고, 계획을 검토하고, 서브에이전트가 보고를 올리는 동안 사용자는 인사 한마디의 답을 기다려야 했다. 여기에 서브에이전트에 자동으로 붙는 기본 미들웨어 — 파일시스템 도구 세트 — 가 계속 사용되면서, 정작 응답에는 드러나지 않는 내부 작업이 지연과 비용만 쌓았다.

원인은 명확했다. 이 프레임워크의 기본값은 "깊게 생각하고 오래 일하는 리서치 에이전트"를 상정한다. 계획 수립도, 범용 서브에이전트도, 파일시스템 미들웨어도 그 시나리오에서는 미덕이다. 하지만 채팅 서비스에서 응답 지연은 그 자체로 결함이다. 해결은 덜어내기였다. 기본 서브에이전트와 파일시스템 미들웨어를 구성에서 제외하고, 우리가 정의한 역할별 서브에이전트만 등록했다. 메인 프롬프트에는 "위임이 필요 없는 단순 대화는 직접 답하라"는 라우팅 기준을 명시했다. 프레임워크의 자율성은 켜고 끄는 것이 아니라 **범위를 지정해주는 것**이라는 걸 이때 배웠다.

## 2라운드 — 랜딩 페이지를 서버에 저장하다

두 번째는 좀 더 황당했다. 사용자가 "html 랜딩 페이지 만들어줘"라고 요청하자, 에이전트가 HTML을 화면에 응답하는 대신 기본 파일시스템 도구인 `write_file`을 호출해 **서버 로컬에 파일로 저장**해버렸다. 에이전트 입장에서는 합리적인 행동이다. "파일을 만들라"는 요청이고, 마침 파일을 쓰는 도구가 손에 쥐여져 있으니까. 하지만 사용자 화면에는 아무것도 나타나지 않고, 서버 어딘가에 아무도 읽지 않을 HTML 파일만 남는다.

이건 1라운드와 같은 뿌리의 문제다. 기본 도구 세트가 우리 도메인과 충돌하는 것. 다른 점은 해결 과정이었다. 기본 도구를 선별적으로 필터링하는 방법이 공식 문서에 제대로 설명되어 있지 않아서, 결국 프레임워크 코드를 직접 열어 도구가 주입되는 경로를 추적한 뒤에야 걷어낼 수 있었다. 이 경험으로 도구 구성 원칙이 하나 생겼다. **도구는 화이트리스트로 관리한다.** 프레임워크가 무엇을 기본 제공하든, 에이전트 손에 들어가는 도구는 우리가 명시적으로 등록한 것뿐이어야 한다. 도구 실행이 코드의 책임이라면(1편), 도구 목록도 코드의 책임이다.

## 3라운드 — 웹 검색 다섯 번

세 번째 증상은 비용으로 왔다. 웹 검색이 필요한 질문 하나에 리서처 서브에이전트가 검색을 다섯 번 넘게 반복했다. 근거를 더 모으려는 성실함이지만, 검색 API는 호출당 과금이고 사용자는 그동안 기다린다. 한 번이면 충분한 질문에 다섯 번의 검색은 품질 향상이 아니라 낭비였다.

이건 프레임워크의 미들웨어 체계로 깔끔하게 풀렸다. 도구 호출 횟수에 상한을 거는 미들웨어를 서브에이전트에 붙이는 것이다.

```typescript
const webSearcher: SubAgent = {
  name: "web_searcher",
  description: "최신 정보 검색과 사실 검증을 담당하는 웹 리서처",
  systemPrompt: webSearcherPrompt(),
  tools: [webSearchTool],
  middleware: [
    // 실행 1회당 web_search 호출을 최대 3회로 제한
    toolCallLimitMiddleware({ runLimit: 3, toolName: "web_search" }),
  ],
};
```

2편에서 "비용의 위 뚜껑을 닫아뒀다"고 쓴 것이 바로 이 장치다. 상한에 걸리면 에이전트는 그때까지 모은 결과로 답을 만든다. 무한히 성실한 에이전트보다 적당히 성실하고 반드시 끝나는 에이전트가 서비스에는 낫다. 모델 호출 자체에도 같은 방식의 상한을 걸어, 위임 구조가 만들 수 있는 최악의 호출 횟수를 상수로 만들었다.

## 4라운드 — 스트리밍이 통째로 깨지다

가장 깊이 파야 했던 문제는 스트리밍이었다. 서브에이전트 구조를 붙인 뒤 어느 날, 프론트 화면에 응답이 한 글자도 나오지 않았다. 로그를 열어보니 스트림은 흐르고 있었다. 다만 우리가 기대한 모양이 아니었다.

이 프레임워크에서 부모 에이전트는 서브에이전트를 `task`라는 **도구**로 호출한다. 위임이 곧 도구 호출인 것이다. 그래서 부모가 서브에이전트를 부르는 순간, 스트림에는 텍스트 대신 도구 호출 인자의 파편이 흘러온다. 당시 로그를 일반화하면 청크 하나가 이렇게 생겼다.

```json
{
  "event": "on_chat_model_stream",
  "data": {
    "chunk": {
      "id": ["langchain_core", "messages", "AIMessageChunk"],
      "kwargs": {
        "content": [],
        "tool_call_chunks": [
          { "type": "tool_call_chunk", "args": "랜", "index": 1 }
        ],
        "tool_calls": [],
        "invalid_tool_calls": [
          { "name": "", "args": "랜", "error": "Malformed args.", "type": "invalid_tool_call" }
        ]
      }
    }
  },
  "metadata": {
    "langgraph_node": "model_request",
    "checkpoint_ns": "model_request:27296781-..."
  }
}
```

뜯어보면 세 가지가 보인다. 첫째, `content`가 비어 있다. 텍스트만 골라 SSE로 내려보내던 핸들러 입장에서는 보낼 것이 없으니 화면이 침묵한다. 둘째, 실제 내용물은 `tool_call_chunks`에 있는데, `args`가 `"랜"` — 인자 JSON이 **한 글자씩 쪼개져** 도착한다. 셋째, 그 파편은 단독으로는 유효한 JSON이 아니므로 매 청크가 `invalid_tool_calls`에 `Malformed args.` 에러로 분류된다. 에러 로그가 청크 수만큼 쏟아지지만, 사실 이건 장애가 아니라 **스트리밍 중인 도구 호출의 정상적인 중간 상태**다. 청크 단위로 파싱하려던 우리 핸들러가 이 상태를 몰랐을 뿐이다.

여기서 1편의 학습 노트가 돌아왔다. tool call 스트리밍은 `tool_call_chunks`를 `index` 기준으로 이어 붙여 완성된 시점에만 파싱해야 한다 — 학습 단계에서 확인만 해두고 쓸 일이 없던 지식이, 프레임워크가 위임을 도구 호출로 구현한 순간 필수 지식이 됐다.

남은 퍼즐은 서브에이전트 자신의 출력이었다. 파편을 다 이어 붙여도 그건 부모가 `task` 도구에 넘긴 인자일 뿐, 서브에이전트가 생성하는 본문이 아니다. 로그를 더 따라가 보니 서브에이전트의 모델 스트림도 같은 `on_chat_model_stream` 이벤트로 흘러오고 있었고, 구분 열쇠는 메타데이터의 체크포인트 네임스페이스에 있었다. 부모의 스트림은 `model_request:...` 단일 경로인데, 서브에이전트의 스트림은 `tools:...|model_request:...` — 도구 실행 컨텍스트 **안에서** 모델이 도는 중첩 경로로 찍힌다. 같은 이벤트라도 발신자의 주소가 다른 것이다.

정리하면 해법은 세 겹이었다. 도구 호출 파편은 index로 누적해 완성 후 파싱하고, 네임스페이스로 부모와 서브에이전트의 스트림을 분리하고, 서브에이전트의 스트림은 본문과 다른 별도 이벤트 타입으로 프론트에 내려보냈다. 프론트는 이를 메시지 마커 하단에 작은 작업 로그로 렌더링한다. 스트리밍 붕괴를 고치다가, 2편 말미에 쓴 "에이전트가 지금 무슨 일을 하는지 보여주는" 가시성의 첫 조각이 얻어걸린 셈이다.

## 배운 것 — 기본값은 우리 도메인을 모른다

네 판을 치르고 남은 결론은 한 문장이다. **프레임워크의 기본값은 우리 도메인을 모른다.** 범용 서브에이전트도, 파일시스템 도구도, 성실한 반복 검색도, 위임을 도구 호출로 감싸는 스트림 구조도 — 어느 것도 버그가 아니었다. 리서치 에이전트라는 원래 시나리오에서는 전부 옳은 설계였고, 채팅 서비스라는 우리 시나리오에서 전부 사고가 됐을 뿐이다.

그래서 프레임워크 채택 기준도 문서의 기능 목록이 아니라 다른 질문들로 바뀌었다. 기본값을 하나씩 끄거나 교체할 수 있는가. 미들웨어 같은 공식 개입 지점이 있는가. 스트림 이벤트에 발신자를 구분할 메타데이터가 충분한가. 돌아보면 이 프레임워크는 기대대로 움직여주지 않았지만, 고삐를 채울 자리는 다 열어두고 있었다. 상한 미들웨어도, 도구 교체도, 네임스페이스 메타데이터도 결국 프레임워크가 제공한 손잡이였다. 좋은 프레임워크란 기본값이 옳은 프레임워크가 아니라, 기본값을 의심할 수 있게 만들어진 프레임워크라는 게 지금의 생각이다.

다음 편은 4라운드에서 얻어걸린 조각을 제대로 키운 이야기다. 서브에이전트의 작업 스트림을 보여주는 수준을 넘어, 에이전트의 실행 과정 전체를 사용자에게 단계별로 중계하는 구조 — 실행 가시성과 Progress Chain을 다룬다.
