## TL;DR

같은 에러를 검색해서 들어온 사람을 위해 결론부터 쓴다. zod v4 스키마를 OpenAI strict structured output에 물렸을 때 400을 만드는 패턴은 네 가지다.

| 패턴 | 에러 메시지 | 해법 |
| --- | --- | --- |
| `discriminatedUnion` | `'oneOf' is not permitted` | `z.union`으로 평탄화 |
| `z.record` | `'propertyNames' is not permitted` | key/value 쌍 배열로 대체 |
| union 안의 `.transform()` | `Transforms cannot be represented in JSON Schema` | transform 제거, 후처리로 이동 |
| `.optional()` | `Missing required keyword` | `.nullable()`로 전환 |

그리고 하나 더. LangChain의 `withStructuredOutput`은 응답을 **zod로 parse하지 않는다**. 스키마는 LLM에게 전달되는 청사진일 뿐, 응답 검증은 호출자 책임이다.

## 머지 직후 400이 폭발했다

기능 브랜치를 통합 브랜치에 머지한 직후, 운영 로그에 OpenAI 400 에러가 폭증하기 시작했다. 에러 메시지는 전부 `Invalid schema for response_format`으로 시작했지만 뒤에 붙는 이유는 제각각이었다. `'oneOf' is not permitted`, `'propertyNames' is not permitted`, `Missing required keyword`.

처음 든 의심은 두 가지였다. "OpenAI가 표준 JSON Schema의 `oneOf`를 거부하는 게 이상한 거 아닌가?" 그리고 "모델을 Anthropic으로 바꾸면 되지 않나?" 실제로 Anthropic으로 바꾸면 에러가 사라졌다. 하지만 이건 해결이 아니라 회피였고, 그 이유는 뒤에서 소스 코드로 확인하게 된다.

진짜 원인은 zod v4가 만드는 JSON Schema와 OpenAI strict 모드의 공식 제약이 구조적으로 충돌한다는 것이었다. 특정 기능 하나의 문제가 아니라, `withStructuredOutput(zodSchema)`을 쓰는 모든 호출처가 잠재 위험이었다.

## strict 모드가 실제로 하는 일

배경을 짚고 가자. OpenAI structured output의 strict 모드는 "응답이 스키마를 100% 준수한다"를 보장하는 대신, 받아주는 JSON Schema에 강한 제약을 건다. 공식 문서 기준으로 `oneOf`, `propertyNames` 같은 키워드를 지원하지 않고, 모든 `properties` 키가 `required` 배열에 들어가야 하며, `$ref`에는 `description`이나 `default` 같은 키워드를 함께 붙일 수 없다.

한편 zod 스키마는 API에 그대로 전달되는 게 아니라 JSON Schema로 변환되어 전달된다. 문제는 zod v3에서 v4로 넘어오면서 이 변환 규칙이 바뀐 항목들이 있다는 것. v3에서는 조용히 통과되던 스키마가 v4에서는 strict 위반 산출물을 만든다. 이제 네 패턴을 하나씩 보자.

## 패턴 1: discriminatedUnion이 oneOf가 된다

zod v3는 `discriminatedUnion`을 `anyOf`로 변환했다. v4는 `oneOf`로 변환한다. strict 모드는 `oneOf`를 거부한다.

```ts
// Before: zod v4 + strict에서 400 (개념 코드)
const filterSchema = z.discriminatedUnion("type", [
  z.object({ type: z.literal("absolute"), start: z.string(), end: z.string() }),
  z.object({ type: z.literal("relative"), intent: z.string() }),
]);

// After: union으로 평탄화하면 anyOf가 된다
const filterSchema = z.union([
  z.object({ type: z.literal("absolute"), start: z.string(), end: z.string() }),
  z.object({ type: z.literal("relative"), intent: z.string() }),
]);
```

평탄화하면 LLM이 `type`으로 분기를 인식하지 못할까 걱정했는데, 각 분기의 `z.literal`이 구분 정보로 충분했다. 운영 e2e에서 정상 분기를 확인했다.

## 패턴 2: z.record가 propertyNames를 만든다

zod v4는 `z.record(z.string(), V)`를 `propertyNames` 키워드가 포함된 스키마로 변환한다. 역시 strict 미지원 키워드다. 해법은 dict를 포기하고 key/value 쌍의 배열로 받는 것이다.

```ts
// Before: 400 (개념 코드)
context: z.record(z.string(), z.unknown())

// After: 배열로 받고 호출자가 복원
context: z.array(z.object({ key: z.string(), value: z.unknown() }))
// 복원: Object.fromEntries(step.context.map((e) => [e.key, e.value]))
```

## 패턴 3: union 안의 .transform()

LangChain core는 스키마를 전달하기 전에 transform의 input 스키마만 추출하려 시도한다. object 안의 transform은 추출에 성공하지만, **union 안에 transform이 있으면** `Transforms cannot be represented in JSON Schema`를 throw한다.

```ts
// Before: throw (개념 코드)
assignee: z.union([z.enum(agentNames), z.string()])
  .transform((v) => (agentNames.includes(v) ? v : null))

// After: transform 없이 표현
assignee: z.enum(agentNames).nullable()
```

변환 로직이 정말 필요하면 스키마가 아니라 응답을 받은 뒤의 후처리 코드로 옮기면 된다.

## 패턴 4: .optional()은 required에서 빠진다

strict 모드는 모든 `properties` 키가 `required`에 포함될 것을 요구한다. `.optional()`은 해당 키를 `required`에서 제외하므로 그 자체로 위반이다. "없을 수 있음"은 전부 `.nullable()`로 표현해야 한다. 키는 항상 존재하되 값으로 `null`을 허용하는 방식이다.

```ts
// Before: Missing required keyword (개념 코드)
mentionedName: z.string().optional()

// After
mentionedName: z.string().nullable()
```

주의할 점 하나. `.default()`는 상황에 따라 다르다. number의 `.default(50)`은 `$ref`를 만들지 않아 안전하지만, **enum에 `.default()`나 `.describe()`를 붙이면 `$ref`와 키워드가 동시 부착되어 위반**이 된다. enum의 설명은 inline으로 풀어 쓰자.

그럼 zod v3로 다운그레이드하면 되지 않을까? 검토 끝에 아니라고 결론 냈다. v3는 패턴 1과 2를 자연 회피할 뿐, 3과 4는 버전과 무관하다. 결국 네 패턴 모두 손봐야 하고, v4의 개선점을 포기하는 비용만 추가된다. v4 유지에 스키마 정제가 정공법이다.

## 라이브러리의 함정: withStructuredOutput은 parse하지 않는다

여기까지 고치고 배포한 뒤에도 회귀가 하나 더 나왔다. `.nullable()`로 바꾼 필드인데 LLM 응답에서 **키 자체가 누락**되어 후단의 zod parse가 깨진 것이다. `.nullable()`은 "키는 있고 값이 null"을 허용할 뿐, 키 누락은 허용하지 않는다.

이상했다. 스키마를 줬는데 왜 누락된 응답이 여기까지 흘러오지? 답을 찾으려면 LangChain 소스를 열어야 했다.

```js
// @langchain/core chat_models 내부 (요지 발췌)
const toolCall = input.tool_calls.find((tc) => tc.name === functionName);
return toolCall.args; // 그대로 반환. zod parse 없음
```

`withStructuredOutput(zodSchema)`의 후처리는 `toolCall.args`를 **그대로 반환**한다. 런타임 zod parse가 없다. 스키마는 JSON Schema로 변환되어 LLM에게 "이 모양으로 응답해라"라고 알려주는 청사진 역할만 한다. 그리고 Anthropic의 기본 모드인 functionCalling 경로는 `input_schema`의 `required`를 API 레벨에서 강제하지 않는다. 앞에서 "Anthropic으로 바꾸면 에러가 사라졌다"의 정체가 이것이다. 검증이 통과된 게 아니라 검증 자체가 느슨했던 것이다.

여기서 얻은 원칙 하나. 트러블슈팅 중에 "우회"라는 단어가 나오면 멈추고 소스로 근본 원인을 추적해야 한다. 우회가 왜 통하는지 설명하지 못하면 그 우회는 언제 깨질지도 모른다.

키 누락 대응은 세 겹으로 했다. 입력 스키마는 `.nullable()` 그대로 유지하고(strict 호환), parse 시점에만 `schema.partial().parse(...)`로 느슨하게 받고, 시스템 프롬프트에 "모든 필드 키를 포함하고 미사용은 null 명시" 규칙을 추가했다.

## 재발 방지: lint 한 겹, 실제 호출 한 겹

같은 위반이 다시 들어오는 걸 막기 위해 테스트를 두 겹으로 깔았다.

**1겹: 스키마 lint 테스트.** 프로덕션 스키마를 실제로 import해서 JSON Schema로 변환한 뒤 재귀 검사한다. `oneOf`와 `propertyNames`의 부재, 모든 object의 properties 키가 required에 포함되는지, `$ref`에 키워드가 동시 부착되지 않았는지, 변환 자체가 throw하지 않는지. 비용이 0이라 매 CI마다 돈다.

**2겹: 실 LLM e2e.** 환경 변수로 opt-in할 때만 실제 OpenAI와 Anthropic API에 `withStructuredOutput`을 호출해 API 거부 시 실패시킨다. 이 테스트가 실제로 lint가 못 잡은 위반 9건을 추가로 잡아냈다. strict 모드에는 문서화되지 않은 미세 규칙이 있어서 **lint 통과가 실 API 통과를 보장하지 않는다.** 정적 검사와 실제 호출, 둘 다 필요하다.

## JSON Schema 제약은 LLM에게 강제되지 않는다

이번 트러블슈팅을 관통하는 교훈은 하나다. **스키마를 정의했다는 것과 그 스키마대로 응답이 온다는 것은 별개의 사실이다.** strict 모드는 스키마를 강제하는 대신 받아주는 스키마를 제한하고, functionCalling 모드는 스키마를 받아주는 대신 준수를 강제하지 않는다. 어느 쪽이든 응답 검증의 최종 책임은 호출자 코드에 있다.

다음 편에서는 이렇게 고쳐놓은 스키마가 시간이 지나며 다시 깨지는 이야기를 쓴다. 라이브러리 버전 업과 스키마 드리프트, 그리고 lint 대상에 등재되지 않은 스키마라는 사각지대다.
