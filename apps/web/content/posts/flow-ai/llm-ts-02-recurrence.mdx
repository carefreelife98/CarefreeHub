## 두 겹을 세웠는데 또 400이 났다

1편에서 zod 스키마와 OpenAI strict 모드가 충돌하는 네 가지 패턴을 정리하고, 재발 방지 장치를 두 겹 세웠다. 스키마를 JSON Schema로 변환해 위반 패턴을 검사하는 lint, 그리고 실제 모델에 strict 호출을 날려보는 opt-in 실 LLM e2e. 이 정도면 같은 문제로 다시 고생할 일은 없겠다고 생각했다.

한 달쯤 지나, 다른 수정 사항을 검증하려고 오랜만에 실 LLM e2e를 돌렸다. 그리고 400을 만났다.

```
400 Invalid schema for response_format:
$ref cannot have keywords {'description', 'title', 'default'}
```

황당한 건 lint였다. 스키마 lint는 전부 통과 상태였다. 첫 번째 겹은 초록불인데 두 번째 겹에서만 빨간불이 켜진 것이다. 그 사이에 있었던 일은 방어 코드 몇 줄 추가와 라이브러리 버전업뿐이었다. 고의로 규약을 어긴 사람은 아무도 없는데, 스키마는 다시 strict가 거부하는 모양으로 돌아가 있었다.

## 범인은 체이닝 순서였다

에러가 가리키는 필드들을 최소 재현으로 좁혀보니, 발동 조건은 딱 하나였다. **zod에서 `.default()` 뒤에 `.describe()`를 체이닝하는 것.**

우리가 쓰는 LLM 클라이언트 라이브러리는 zod 스키마를 JSON Schema로 변환할 때 기본 옵션이 아니라 `reused: 'ref'` 계열 옵션을 쓴다. 이 경로에서 `.default()` 래퍼 뒤에 `.describe()`가 붙은 필드는 `$defs`로 호이스팅되어 `$ref` 참조로 바뀌고, 그 `$ref` 노드에 `default`, `description`, `title`이 형제 키워드로 함께 붙는다. OpenAI strict는 형제 키워드가 붙은 `$ref`를 400으로 거부한다.

같은 옵션으로 로컬에서 재현해 정리한 매트릭스는 이랬다.

| zod 패턴 | $ref 호이스팅 | strict 판정 |
| --- | --- | --- |
| `z.enum([...]).default('x').describe('..')` | 발생 | 400 |
| `z.enum([...]).describe('..').default('x')` | 없음 | 통과 |
| `z.string().nullable().default(null).describe('..')` | 발생 | 400 |
| `z.string().describe('..').nullable().default(null)` | 없음 | 통과 |
| `z.number().min().max().default(50).describe('..')` | 발생 | 400 |
| 형제 키워드 없는 bare `$ref` | 발생 | 통과 |

세 가지가 뼈아팠다. 첫째, 두 체이닝 순서는 **zod parse 의미가 완전히 동일하다.** 키가 빠지면 default로 채워지는 동작은 어느 쪽이든 같다. 의미가 같으니 코드 리뷰에서 걸릴 리 없다. 둘째, 1편 당시 "number의 default는 안전하다"고 실측까지 해서 기록해 뒀는데, 라이브러리 버전업으로 그 기록이 무효가 됐다. 셋째, 마지막 줄이 보여주듯 `$ref` 자체는 죄가 없다. 형제 키워드가 붙었을 때만 죽는다. 검출 규칙을 "$ref가 생기면 실패"로 만들면 멀쩡한 스키마까지 잡는 과잉 검출이 된다.

수정 자체는 허무할 만큼 간단했다. 문제 필드들의 체이닝 순서를 `.describe()` 먼저, `.default()` 나중으로 바꾸면 끝이다. 파싱 의미는 그대로고 `$ref`는 생기지 않는다.

## lint는 왜 못 잡았나: 검출 규칙의 사각

진짜 질문은 이거였다. 첫 번째 겹인 lint는 왜 초록불이었나.

답은 변환 옵션이었다. lint는 zod 스키마를 **기본 옵션**으로 JSON Schema로 변환해 검사하고 있었다. 기본 옵션은 재사용 노드를 inline으로 풀기 때문에 `$ref`가 아예 생기지 않는다. 반면 실제 API 호출 경로의 변환기는 `reused: 'ref'`로 동작한다. 같은 스키마인데 lint가 보는 산출물과 API에 실제로 나가는 산출물이 서로 달랐던 것이다. 검사는 성실하게 돌았지만, **발행물이 아니라 다른 물건을 검사하고 있었다.**

그래서 lint를 실경로와 동일한 옵션으로 변환해 `$ref` 노드의 형제 키워드를 검출하도록 고쳤다. bare `$ref`는 실 API가 허용하므로 통과시킨다. 검출 범위를 실 API의 허용 범위와 1:1로 맞춘 것이다. 이 검사는 이후 같은 패턴을 담은 다른 브랜치가 합류할 때 실제로 빌드를 깨뜨리며 같은 수정을 강제했다. 이번엔 사람의 기억이 아니라 규칙이 일했다.

## 두 번째 사건: 스키마가 두 곳에 살고 있었다

일주일쯤 뒤, 이번엔 운영 로그에서 에러가 올라왔다.

```
Domain notification failed:
expected string, received null (dateFilter.startDate)
```

알림 검색 요청이 통째로 빈 결과를 내고 있었다. 그런데 이번엔 LLM의 출력 자체는 **완벽하게 합법이었다.** "오늘까지 온 알림"처럼 상한만 있는 기간 질의에 대해 모델은 `{ startDate: null, endDate: ... }`를 냈고, 이건 strict가 문법으로 보증한, LLM에게 준 스키마상 정확히 허용되는 출력이었다.

죽인 건 내부였다. LLM 출력을 받아 API 파라미터로 바꾸기 전에 한 번 더 검증하는 내부 parse 스키마에서는 `startDate`가 non-null이었다. **같은 필터 스키마가 두 곳에 살고 있었던 것이다.** LLM에게 보여주는 nullable 버전과, 내부 검증용 non-null 버전.

이 이원화의 출처를 따라가니 앞의 사건과 이어졌다. 예전에 strict 400이 났을 때, 아직 체이닝 순서라는 근본 원인을 모르던 시점에 "LLM 전용 스키마를 따로 만들어 우회"한 것이 시작이었다. 그 파일엔 `SYNC: 수동 동기화 필요`라는 주석이 붙어 있었다. 지금 보면 이 주석은 드리프트의 예고이자 자백이었다. 수동 동기화가 필요하다는 말은, 언젠가 동기화가 깨진다는 말과 같다.

얄궂은 디테일도 있었다. parse 바로 다음 줄의 날짜 처리 코드는 이미 null을 안전하게 다루고 있었다. 소비하는 쪽은 준비가 돼 있는데 문지기가 먼저 죽는 구조였다. 그리고 실 API 검증을 돌려보니 `startDate`만이 아니었다. 다른 두 필드도 LLM 쪽은 nullable, 내부는 non-null이었고 모델이 실제로 null을 출력하는 것까지 확인됐다. 아직 관측되지 않았을 뿐, 같은 클래스의 장애가 두 건 더 대기 중이었다.

## 청산: 단일 소스 + 파생 뷰

수정 방향은 "동기화를 잘하자"가 아니었다. **동기화할 대상 자체를 없애는 것.** 두 스키마를 공유 계약 패키지의 스키마 하나로 병합했다. nullability는 LLM 쪽 기준으로 정합을 맞추고, LLM용 사본에만 있던 풍부한 설명 텍스트도 프롬프트 자산이므로 함께 병합했다. null의 도메인 기본값 해석은 스키마가 아니라 소비자 코드의 `??`가 맡는다.

LLM에게 보여주는 뷰는 파생으로만 만든다.

```typescript
// 단일 소스: 공유 계약 패키지에 한 곳만 존재한다
export const notificationFilter = z.object({ /* ... */ });

// LLM 뷰: omit 파생만 허용, 필드 재정의 금지.
// projectIds처럼 LLM이 지어내면 안 되는 필드만 제외한다
export const notificationFilterForLlm = notificationFilter.omit({
  projectIds: true,
});
```

여기서도 규칙만 만들고 끝내지 않았다. 파생 뷰가 원본과 동일 인스턴스인지, 파생 뷰의 shape가 정확히 "원본 빼기 제외 필드"인지 검사하는 보증 테스트를 넣었다. 누군가 파생 뷰에 필드를 재정의하는 순간, 즉 스키마가 다시 두 곳에 살기 시작하는 순간 테스트가 실패한다. 장애를 낸 출력 세 형태는 회귀 테스트와 실 e2e 배터리에 박아 넣었다.

## 재발은 수정 누락이 아니라 구조의 성질이다

두 사건을 겪고 나서 정리한 결론은 이렇다. 재발은 누가 게을러서 생기는 게 아니다. **구조가 허용하면 반드시 생긴다.**

첫째, **스키마가 N곳에 살면 드리프트는 시간문제다.** 코드 사본만 스키마가 아니다. lint가 보는 변환 산출물과 API에 나가는 변환 산출물이 다르면 그것도 이원화다. 첫 사건은 산출물의 이원화였고, 둘째 사건은 소스의 이원화였다. 형태만 달랐지 같은 병이다.

둘째, **검출 규칙은 알려진 패턴만 잡는다.** lint는 만든 시점의 지식 스냅샷이다. 라이브러리 버전업 하나로 "안전하다"던 기록이 무효가 됐다. 그러니 검출 규칙은 한 번 만들고 끝나는 게 아니라 사례가 생길 때마다 확장하는 자산으로 다뤄야 한다.

셋째, **검증은 발행물 기준으로 한다.** 검사 대상은 소스가 아니라 실제로 상대방에게 전달되는 산출물이어야 하고, 검사 조건은 실경로와 동일해야 한다. lint 통과와 실 API 통과는 다른 명제다. 이 간극을 메우는 건 실경로 재현 검사와 실 LLM e2e다.

## 실용 체크리스트

- 스키마는 한 곳에만 둔다. "LLM 전용 사본"이 생기는 순간 시한폭탄이 설치된 것이다.
- 변형이 필요하면 `omit`, `pick` 같은 파생으로만 만들고, 파생 뷰의 필드 재정의를 테스트로 차단한다.
- null의 기본값 해석은 스키마 default가 아니라 소비자 코드에 둔다. 스키마는 "무엇이 합법인가"만 말하게 한다.
- 스키마 lint는 실제 호출 경로와 동일한 변환 옵션으로 검사한다. 기본 옵션 변환 결과는 발행물이 아니다.
- 검출 규칙은 사례가 생길 때마다 확장한다. 새 장애 하나에 새 검사 하나가 원칙이다.
- 실 LLM e2e를 opt-in으로라도 유지하고, 장애를 낸 실제 출력은 회귀 케이스로 박아 넣는다.

## 다음 편

스키마 이야기는 여기까지다. 다음 편은 결이 다른 단편 모음이다. 멀쩡한 문자열이 모델을 지나며 깨지는 인코딩 함정, 그리고 그럴듯한 얼굴로 없는 사실을 만들어내는 환각과 싸운 기록을 묶는다.
