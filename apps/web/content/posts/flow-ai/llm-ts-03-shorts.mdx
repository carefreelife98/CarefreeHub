## 단편 모음으로 마무리한다

이 시리즈의 1편은 zod와 OpenAI strict 모드의 호환성 4패턴을, 2편은 그 문제의 재발과 드리프트를 다뤘다. 완결편인 이번 글은 형식이 다르다. 하나의 큰 사건 대신, 각각 따로 검색해서 도착해도 읽히는 짧은 트러블슈팅 세 건을 묶었다. 인코딩(이모지 반쪽), 환각(enum에 없는 값), 스키마 손상(union이 변환 중에 부서지는 문제)이다. 세 건 모두 LLM 파이프라인을 운영하면 언젠가 만나게 되는 부류이고, 공교롭게도 결론은 하나로 모인다.

## 단편 1. 이모지 반쪽이 OpenAI 400을 만든다

어느 날 운영 로그에서 AI 검색의 결과 검증 노드가 이런 에러로 쓰러져 있었다.

```
400 Invalid 'input[1].content': string contains an unpaired
UTF-16 surrogate code point and cannot be encoded as valid UTF-8
```

검증 호출이 실패하자 키워드 재생성으로 재시도했는데, 그것도 똑같은 400이었다. 두 호출이 같은 검색 결과 본문을 프롬프트에 공유하고 있었기 때문이다. 결과 자체는 폴백으로 반환됐지만, 관련성 검증과 재시도 체계가 통째로 무력화된 상태였다.

### 서로게이트 쌍 기초

JavaScript 문자열은 UTF-16이다. 기본 다국어 평면(BMP) 밖의 문자, 대표적으로 대부분의 이모지는 코드 유닛 두 개의 쌍으로 표현된다. 😀는 `U+D83D` `U+DE00` 두 유닛이고, 앞쪽(`D800`\~`DBFF`)을 high surrogate, 뒤쪽(`DC00`\~`DFFF`)을 low surrogate라고 부른다. 이 쌍이 깨져서 한쪽만 남은 것이 lone surrogate다. 문자열로서는 존재할 수 있지만, UTF-8로는 인코딩할 수 없는 값이다.

lone surrogate가 생기는 경로는 두 가지였다. 첫째, 외부 데이터. 검색 대상 본문에 이미 깨진 문자가 섞여 들어와 있었다. 둘째, 우리가 직접 만들고 있었다. 프롬프트 길이를 제한하는 자르기 유틸이 `slice`를 쓰고 있었는데, `slice`는 코드 유닛 단위로 자르기 때문에 경계에 이모지가 걸리면 쌍을 반으로 절단한다.

```typescript
const text = "가".repeat(1996) + "😀";
const cut = text.slice(0, 1997);
// 마지막 문자는 U+D83D, 짝을 잃은 high surrogate

JSON.stringify(cut); // 예외 없이 통과한다. U+D83D 이스케이프 텍스트로 남을 뿐
```

여기가 함정이다. `JSON.stringify`는 lone surrogate를 거부하지 않는다. 이스케이프해서 문법상 유효한 JSON 텍스트를 만들어준다. 직렬화 단계에서는 아무 일도 없다가, HTTP 전송을 위해 UTF-8 바이트로 인코딩하는 순간 API 서버가 거부한다. 로컬에서 재현이 안 되고 운영에서만 터지는 전형적인 이유다.

### 해법: 전송 직전 단일 지점에서 정제

수정은 두 겹으로 했다. 자르기 유틸은 서로게이트 경계를 인식하는 `safeTruncate`로 바꿔 절단 자체를 막고, 프롬프트에 들어가는 모든 외부 문자열이 통과하는 스니펫 빌더 한 곳에서 lone surrogate를 일괄 제거했다.

```typescript
// ES2024: 표준 API가 가장 안전하다
const sanitize = (text: string) =>
  text.isWellFormed() ? text : text.toWellFormed();

// 구형 런타임: 코드 포인트 순회에서 lone surrogate만 걸러낸다
// (문자열 이터레이터는 정상 쌍을 길이 2로, 외톨이는 길이 1로 돌려준다)
const sanitizeLegacy = (text: string) =>
  Array.from(text, (ch) => {
    const code = ch.charCodeAt(0);
    const isSurrogate = code >= 0xd800 && code <= 0xdfff;
    return isSurrogate && ch.length === 1 ? "" : ch;
  }).join("");
```

뼈아팠던 건, 같은 부류의 방어가 DB 저장 경로에는 이미 있었다는 점이다. LLM 전송 경로만 사각지대였다. 교훈은 두 개다. 외부 출처 문자열은 필드별로 산발 처리하지 말고 전송 직전 chokepoint 한 곳에서 정제할 것. 그리고 한쪽 경로에 인코딩 가드를 넣었다면 같은 데이터가 흐르는 다른 경로도 반드시 점검할 것.

## 단편 2. 스키마에 있다고 지키는 건 아니다

모니터링에서 웹 검색 도구의 에러 두 건이 나란히 잡혔다. 둘 다 원인은 모델이었다.

첫 번째는 enum 환각. 검색 기간 타입 필드는 `none | latest_year | latest_quarter | latest_half | specific_period`의 다섯 값만 받는데, 모델이 `latest_month`를 반복해서 만들어냈다. 스키마에도 없고 프롬프트에도 없는 값이다. 월 단위 개념이 설계에 없다는 사정은 모델에게 중요하지 않았다. 그럴듯하니까 생성했을 뿐이다.

두 번째는 날짜 역전. 검색 범위의 시작일에 미래 날짜를, 종료일에 과거 날짜를 넣어서 외부 검색 API가 "after는 before보다 앞서야 한다"며 400을 던졌다. 그래프 실패 후 폴백 경로도 같은 값을 그대로 썼기 때문에 똑같이 실패했다.

두 건의 공통점은 이것이다. 스키마와 프롬프트는 모델에 대한 요청이지 보장이 아니다. "스키마에 정의돼 있다"와 "모델이 지킨다" 사이에는 항상 간극이 있고, 그 간극은 코드로 메워야 한다.

enum은 reject 대신 근사 매핑으로 방어했다. 검색을 실패시키는 것보다 가장 가까운 값으로 성공시키는 편이 사용자에게 낫다고 판단했다.

```typescript
const periodType = z.preprocess(
  (v) => (VALID_PERIODS.includes(v as string) ? v : "latest_quarter"),
  z.enum(["none", "latest_year", "latest_quarter", "latest_half", "specific_period"]),
); // latest_month가 와도 분기 근사로 살린다
```

날짜는 정규화 순서가 핵심이었다. 스왑을 먼저 해야 미래 날짜가 after 자리에 왔을 때 before 쪽으로 옮겨져서 clamp에 잡힌다.

```typescript
if (after > before) [after, before] = [before, after]; // ① 스왑 먼저
if (before > now) before = now;                        // ② 미래를 현재로 clamp
if (after > before) after = defaultAfter(before);      // ③ 어긋나면 재조정
```

LLM의 출력을 받는 코드는 파서라기보다 방어선이다. 유효하지 않은 값이 "올 수도 있다"가 아니라 "반드시 온다"를 전제로 짜야 한다.

## 단편 3. 변환 계층을 지날 때마다 스키마는 원형을 잃는다

워크플로우 실행기가 MCP 도구를 호출할 때마다 서버가 입력을 거부하는 문제였다. 날짜 필터는 type-tagged union으로 정의돼 있었다. `type: 'none'`이면 그걸로 끝이고, `type: 'explicit'`이면 `startDate`가 필수인 구조다. 그런데 도구 인자를 채우는 LLM이 매번 `{ type: 'explicit' }`만 보내고 `startDate`를 빠뜨렸다. 서버 측 zod가 정확하게 reject했고, 워크플로우 노드는 매번 실패했다.

이상한 점은 클라이언트 측 검증은 통과한다는 것이었다. 스키마를 덤프해보니 이유가 보였다. 서버가 보낸 원본은 `anyOf` 두 분기가 살아 있는 union인데, 클라이언트에 도착한 것은 분기가 사라진 단일 object였다.

```json
{
  "type": "object",
  "properties": {
    "type": { "type": "string" },
    "startDate": { "type": "string", "pattern": "^\\d{8}$" },
    "endDate": { "type": "string", "pattern": "^\\d{8}$" }
  },
  "required": ["type"]
}
```

`startDate`가 required에서 사라져 있다. 범인은 중간의 변환 계층이었다. `@langchain/mcp-adapters`(당시 1.1.3)가 OpenAI strict 모드 호환을 위해 union을 단순화한다. 모든 분기의 properties를 하나로 합치고, required는 분기들의 교집합을 취한다. `['type']`과 `['type', 'startDate']`의 교집합은 `['type']`이다. 라이브러리 입장에서는 의도된 동작이지만, type-tagged union에서는 필수 키가 소실되는 부작용이 된다. 손상된 스키마를 본 LLM은 `startDate`를 optional로 판단했고, 그 판단은 스키마 기준으로는 완벽하게 합리적이었다.

원인을 찾는 과정에서 배운 게 하나 더 있다. zod의 JSON Schema 직렬화, MCP SDK의 버전 바인딩, 역직렬화의 required 보존까지 그럴듯한 가설을 네 개나 세웠는데 전부 틀렸다. 각 변환 단계의 실제 출력을 덤프해서 비교하고 나서야 정답이 나왔다. 변환 계층의 동작은 추론하지 말고 실험으로 확인해야 한다.

수정은 어댑터 우회였다. 변환 결과 대신 MCP 클라이언트의 raw `listTools()`를 직접 호출해 원본 inputSchema와 outputSchema를 그대로 카탈로그에 실었다. 프롬프트에 "부분 입력 금지" 규칙을 강화하는 것도 해봤지만 보조 가드일 뿐이었다. 손상된 스키마를 주고 가이드로 막는 것보다, 진짜 스키마를 주는 것이 본질이다.

일반화하면 이렇다. 스키마가 직렬화, 어댑터, 역직렬화를 거치는 파이프라인에서는 계층 하나하나가 원형을 훼손할 수 있는 용의자다. 최종적으로 소비자(LLM이든 검증기든)에게 도착한 발행물이 원본과 같은지 검증하는 습관이 필요하다.

## 시리즈를 닫으며

세 단편의 표면은 제각각이다. 유니코드 인코딩, 모델 환각, JSON Schema 변환. 하지만 1편의 strict 모드 4패턴부터 이번 단편들까지, 시리즈를 관통한 교훈은 결국 하나였다.

**모델도 파이프라인도 문서만큼 믿지 마라. 검증은 코드로 해라.**

스키마는 요청이지 보장이 아니고(단편 2), 직렬화는 인코딩 가능을 보장하지 않으며(단편 1), 변환 계층은 원형을 보존하지 않는다(단편 3). 세 문장 모두 "문서상으로는 되는 것"과 "실제로 벌어지는 것"의 간극에서 나왔고, 그 간극을 메운 것은 매번 문서가 아니라 sanitize 함수, preprocess 폴백, raw 스키마 검증 같은 코드였다.

이 번외 시리즈는 여기서 완결이다. 각 사건이 벌어진 무대가 궁금하다면 본편 시리즈로 이어진다. 단편 1의 AI 검색 파이프라인은 [플로우 AI 검색 개발기](/series/flow-ai-search)에서, 단편 3의 MCP 서버와 카탈로그는 [Flow MCP 개발기](/series/flow-mcp)에서 처음부터 다뤘다. 같은 400을 만난 누군가가 검색으로 이 글에 도착했다면, 그걸로 이 단편 모음은 제 몫을 한 것이다.
