## 월요일 아침, 빈 디렉터리에서 시작했다

1편의 끝에서 예고한 대로다. 2026년 4월 21일 월요일에 설계를 시작해서, 목요일 밤에는 운영 데이터가 Claude 안에서 조회되고 있었다. 설계, 구현, EC2 배포, 운영 연동까지 나흘. 혼자였다.

타임라인만 요약하면 이렇다.

- **월요일:** 설계. brainstorming → spec → plan 3단계로 설계 문서를 완성하고 Phase 1 범위를 확정했다. 검색 8개 + 조회 3개, 도구 열한 개.
- **화요일:** 구현. NestJS 위에 MCP 서버 앱 skeleton을 세우고, Streamable HTTP transport와 API Key 인증, 도구들을 붙였다.
- **수요일:** 머지와 배포. 여기서 사고가 연쇄로 터졌다. 저녁 10시에야 `/health`가 200을 돌려줬다.
- **목요일:** 운영 연동. 새벽에 운영 데이터 조회 경로를 뚫고, 오전에 캐시 사고를 수습했다.

빠르게 달린 만큼 빚도 쌓였다. 이 글은 그 나흘의 기록이고, 마지막 절은 그 빚의 목록이다.

## 설계 하루: brainstorming, spec, plan

나흘 중 하루를 통째로 설계에 쓴 것이 결과적으로 이 스프린트를 가능하게 했다. 방식은 AI와의 협업을 전제로 한 3단계였다. 먼저 **brainstorming으로** 문제 공간을 넓게 흩어놓고, **spec으로** "무엇을 만들 것인가"를 좁히고, 마지막 **plan에서** 태스크 단위의 실행 계획으로 내렸다. plan 문서는 체크박스가 달린 30개 태스크로 끝났는데, 각 태스크에 수정할 파일·검증 커맨드·커밋 메시지까지 박혀 있어서 다음 날의 구현은 사실상 "계획을 소비하는 일"이 됐다.

이 과정에서 흥미로웠던 건 설계 논쟁이었다. 담당자별·업무별로 나뉘어 있던 세 개의 사람 필터 스키마를 두고, 초안은 "역할이 다르니 분리 유지"를 주장했다. 나는 "type 자체가 확장될 수 있는 형태여야 한다"고 피드백했고, 재검토 끝에 하나의 통합 필터(개념 코드: `PersonFilter`)로 합쳤다. 초기 판단을 뒤집은 이 결정은 이후 도구가 늘어날 때마다 옳았음이 증명됐다. 같은 개념은 하나로 두는 쪽이 확장에 열려 있다.

스키마의 단일 원본을 담을 공유 라이브러리의 이름도 이때 정해졌다. 처음 제안된 "data-core" 류의 이름 대신 **계약(contract)** 이라는 단어를 골랐다. 이 라이브러리가 담는 건 데이터가 아니라 "MCP 서버와 기존 API가 합의한 스키마"라는 의미 단위였기 때문이다. 이름이 구조를 설명하게 만드는 것, 설계 문서에서 가장 오래 남은 소득 중 하나다.

그리고 이날, 이후 모든 사고의 뿌리가 될 결정도 함께 내려졌다. 기존 API 앱 안에 있던 전략(Strategy)·API 호출부·이름 해석기 구현을 그대로 두고, 새 MCP 앱이 **path alias로 직접 참조하게** 한 것이다. 당시엔 빠르게 가는 지름길로 보였다.

## 사건 1: path alias가 낳은 의존성 전염

수요일 배포에서 그 지름길이 청구서를 내밀었다.

**증상:** EC2에서 컨테이너를 띄우면 매번 다른 모듈이 없다며 죽었다. Prisma 런타임 유틸 누락으로 시작해서, OpenTelemetry API, winston과 그 플러그인들, nestjs-cls, dayjs까지, 하나 추가하고 재배포하면 다음 에러가 나오는 두더지 잡기를 여섯 번 반복했다. 3시간이 사라졌다.

**원인:** MCP 앱은 기존 API 앱의 로거 클래스 하나를 참조했을 뿐인데, 그 로거가 winston을, winston이 OpenTelemetry를 끌고 왔다. 핵심은 NestJS의 class token DI가 **type import가 아니라 런타임 import라는** 점이다. 타입만 빌리는 줄 알았던 참조가 실제로는 상대 앱의 의존성 그래프 전체를 프로덕션 런타임으로 끌고 들어온다. 중간에 로거를 어댑터로 감싸 끊어보려 했지만, class token이 있는 한 원본 클래스 파일의 import는 여전히 실행됐다. 어댑터는 무효였고, 결국 전염된 의존성을 package.json에 하나씩 명시하는 방향으로 회귀했다. 덤으로 두 앱의 빌드 도구가 달라서(한쪽은 SWC, 한쪽은 tsc) 타입 선언 파일이 비는 문제까지 겹쳤다.

**교훈:** 공유 코드는 path alias가 아니라 **라이브러리로 추출해야** 한다. 그래야 각 앱의 의존성 명세가 독립적이고 명시적이 된다. 이건 당시에 이미 알고 있었지만 "1~2일 작업"이라 미뤘고, 그 유예가 이 글 마지막 절의 빚 목록 첫 줄이 된다.

## 사건 2: 46개 커밋을 squash한 대가

배포 전날, develop 히스토리를 깔끔하게 만들겠다고 46개의 원자 커밋을 하나로 squash했다. 결과는 **조용한 누락 3건이었다.** Prisma 스키마의 API 키 모델 하나, 공유 라이브러리 barrel export 2줄, 그리고 lockfile에 새 앱의 의존성 25개. 셋 다 빌드가 아니라 배포 단계에서야 증상으로 나타났고, 하나씩 발견해 수동 복구하다가 "더 있을 수 있다"는 생각이 들었다.

그 시점에 복구 전략을 바꿨다. squash 커밋을 revert하고, feature 브랜치를 `--no-ff`로 다시 머지했다. 히스토리는 지저분해졌지만 46개 원자 커밋이 전부 보존됐고, 충돌 4건을 손으로 풀고 나니 누락은 사라졌다. 1시간을 썼지만 지금도 옳은 판단이었다고 생각한다. **깔끔한 히스토리와 정보 보존이 충돌하면 정보 보존이 이긴다.**

교훈은 두 개다. squash는 변경이 작고 독립적일 때만 쓸 것. 46커밋을 한 번에 누르는 건 도박이다. 그리고 squash를 했다면 `git diff <squash-commit> <feature-branch>`로 반드시 원본과 비교할 것. 이 한 줄이면 누락 3건은 배포 전에 잡혔다.

## 사건 3: CloudFront가 52분 동안 기억한 응답

목요일 오전의 사고는 성격이 달랐다. 코드도 머지도 아닌, 인프라의 기본값이 문제였다.

**증상:** 관리자 화면에서 MCP 키를 폐기했는데, 목록에는 여전히 활성으로 보였다. DB를 직접 보면 폐기 시각이 정확히 박혀 있었다.

**원인:** 관리자용 키 목록 GET API에 `Cache-Control` 헤더가 없었다. CloudFront가 기본 캐시 정책으로 그 응답을 edge에 물고 있었고, 폐기 후에도 52분 동안 옛 응답을 재사용했다. 서버는 멀쩡했고, 세상이 그 사실을 모르고 있었을 뿐이다.

**해결은** 5줄이었다. 해당 GET 엔드포인트들에 `no-store` 헤더를 붙였다. 하지만 이건 핫픽스지 해결이 아니다. 관리자·실시간 API는 **기본이 no-store여야 하고,** 그건 컨트롤러마다 사람이 헤더를 붙이는 방식으로는 보장되지 않는다. 전역 인터셉터든 CDN behavior의 TTL 0이든, 사람의 기억에 의존하지 않는 구조가 필요했다. 이것도 빚 목록에 올라갔다.

이 밖에도 자잘한 사고가 많았다. 배포 스크립트가 interactive 프롬프트에 걸려 9분간 멈춰 있던 것(이후 `CI=1`을 강제했다), 스크립트가 하드코딩한 `.env` 경로와 docker compose CLI 이름이 실제 서버와 달랐던 것. 공통 교훈은 하나다. **환경에 대한 가정은 하드코딩이 아니라 감지(detect) 전략이어야 한다.**

## 남은 빚: 당시 기준의 솔직한 목록

목요일 밤, 나는 미해결 이슈와 기술부채를 한 문서에 몰아 적었다. "운영 정식 분리 때 한꺼번에 청소한다"는 조건과 함께. 아래는 그 목록의 요약이다. **어디까지나 2026년 4월 24일 기준이고,** 상당수는 이후 시리즈에서 갚아나가는 과정이 나온다.

- **공유 라이브러리 미추출:** 의존성 전염의 근본 원인을 알면서도 path alias 구조를 유지했다. 해결 전까지 같은 유형의 사고가 반복될 것이라고 스스로 적어뒀다.
- **운영 연동 임시 장치 3종:** 개발 인프라에서 운영 데이터를 조회하기 위해, 호출 단위 운영 라우팅 옵션, 백오피스의 "운영 유저 검색·발급 (임시)" 탭, 그리고 키 테이블의 일부 컬럼에 본래 의미와 다른 값을 채우는 스키마 타협까지. 전부 "임시"라는 라벨을 붙였지만, 임시가 얼마나 오래 사는지는 모두가 안다. 참고로 전역 환경변수로 모든 트래픽을 운영으로 우회시키는 방식을 먼저 만들었다가, 공유 개발 서버에서는 사고 그 자체라는 걸 깨닫고 호출 단위 옵션으로 재설계했다.
- **보안 경계의 부채:** 운영 환경의 자격증명이 개발 인프라 쪽에 임시로 놓이는 형태의 부채가 하나 있었다. 좌표는 적지 않는다. 유형만 말하면 "환경 분리 원칙의 임시 위반"이고, 운영 전용 서버 분리 배포가 끝나면 즉시 제거하는 조건이었다.
- **관리자 API 캐싱 전역 정책 부재:** no-store를 붙인 건 사고가 난 컨트롤러뿐. 나머지 관리자 API는 여전히 무방비였다.
- **레거시 게이트웨이 대신 정식 API로:** Phase 1은 사내 레거시 게이트웨이를 경유해 데이터를 읽었다. 운영 첫 호출부터 그 게이트웨이의 내부 오류로 막혀 담당 팀 협의로 풀었는데, 이 경험이 "코드로 해결 안 되는 문제를 빨리 인식하라"는 교훈과 함께, 이후 정식 OpenAPI로 전환하는 로드맵의 복선이 됐다.

나흘 만에 서버는 섰다. 하지만 위 목록을 다시 읽어보면, 선 것은 서버지 구조가 아니었다.
