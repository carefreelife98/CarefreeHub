## 카탈로그 연대기

3편은 아키텍처 결정 여섯 개로 끝났다. 뼈대가 섰으니 다음은 살이다. 도구를 몇 개, 어떤 굵기로 깎을 것인가.

결론부터 말하면 도구 개수는 단조 증가하지 않았다. 11개로 시작한 카탈로그는 18, 27, 32, 36을 거쳐 48개(11개 도메인)가 됐고 이후 60개까지 불었다가 47개로 다시 줄었다. 늘린 것도 의도였고, 쪼갠 것도 의도였고, 다시 합친 것도 의도였다. 다만 각 시점의 의도가 서로 반대 방향을 가리켰다는 게 이 편의 이야기다.

```mermaid
flowchart LR
    A[11<br/>레거시 게이트웨이] --> B[18<br/>OpenAPI 첫 7종]
    B --> C[32<br/>검색 재구성]
    C --> D[36<br/>목록 도구 분리]
    D --> E[48<br/>11도메인 · 4종 백엔드]
    E --> F[60<br/>채팅 등 증식]
    F --> G[47<br/>16종을 3종으로]
```

## 레거시 게이트웨이에서 OpenAPI로

카탈로그가 자라기 전에 먼저 발밑을 갈아야 했다. 초기 11개 도구 중 9개는 사내 레거시 내부 게이트웨이를 경유했다. 환경변수에 심은 공유 인증 키 하나로 우회 호출하는 구조라 빨리 세우기엔 좋았지만 외부 LLM 호스트가 물릴 공식 표면으로는 아니었다. 회사의 정식 OpenAPI는 기업 단위 키 발급, plan과 구독 상태, IP와 Operation 화이트리스트까지 자체 검증한다. 이 표준 위로 올라타는 게 맞았다.

그래서 "전면 전환" 로드맵을 세웠는데, OpenAPI 스펙을 정밀 대조하자마자 계획이 깨졌다. 11개 도구 중 1:1 매핑이 되는 건 단 하나. 몇 개는 입출력 변환을 끼우면 부분 매핑이 됐고 나머지 다수는 **대응 endpoint 자체가 없었다.** 전면 전환은 사실상 불가라는 판정이었다.

전략을 선회했다. OpenAPI로 갈 수 있는 것만 옮기고 나머지는 각자 맞는 백엔드에 남긴다. 대신 원칙을 하나 박았다. **도구마다 백엔드를 컴파일 타임에 고정한다.** 런타임 분기나 fallback 없이, 모듈의 전략 바인딩만 보면 이 도구가 어디를 때리는지 즉시 보이게. 도구는 얇은 shell이고 로직은 전략 객체가 들고 있어서 백엔드 교체는 DI 바인딩 한 줄로 끝난다. 3편의 Strategy 패턴 결정이 여기서 처음으로 본전을 뽑았다.

그 결과가 48개 시점의 **4종 백엔드 공존이다.** 읽기·검색·표준 쓰기 36개는 OpenAPI, 프로젝트와 조직의 멀티홉 컨텍스트 수집 5개는 DB 직접 조회, OpenAPI에 대응 endpoint가 없는 쓰기 6개는 레거시 게이트웨이 존치, 생성형 이미지 1개는 AI 백엔드 내부 호출. 지금 돌아보면 "단일 백엔드로 수렴"이라는 처음 그림보다 이 편이 정직하다. 백엔드는 도구의 사정에 맞추는 것이지, 도구를 백엔드의 사정에 맞추는 게 아니었다.

### 키 하나 조회하는 데 안전망이 세 겹

OpenAPI 전환의 실제 난관은 endpoint 매핑이 아니라 키 관리였다. 기업 단위로 발급되는 OpenAPI 키를 MCP 서버가 대신 조회해 실어 보내야 했는데, 이 키의 lifecycle 전체를 감당하는 3-Layer 안전망을 설계했다.

- **Layer 1, 발급 시점:** 사용자가 MCP 키를 발급받으려 할 때 소속 기업의 OpenAPI 키 존재를 사전 검증한다. 없으면 발급 거부. 쓸 수 없는 키를 만들어주지 않는다.
- **Layer 2, 호출 시점:** 캐시 우선 lookup. 캐시 미스가 몰리면 single-flight로 DB 조회를 한 번만 보내고 존재하지 않는 키는 음성 캐싱으로 폭주를 흡수한다.
- **Layer 3, 응답 시점:** 401이 오면 캐시를 폐기하고 fresh 조회로 1회 재시도한다. 새로 가져온 키가 다르면 캐시가 낡았던 것이니 자가치유. 같은 키라면 키 자체가 무효라는 뜻이라 그 기업의 MCP 키를 일괄 revoke하고 실패를 알린다.

두 시점 모두 hard-fail이다. 어중간하게 성공한 척하는 것보다 명확하게 거절하는 쪽이 운영을 살린다고 판단했다. 이 판단이 한 달 뒤 사고로 되돌아오는데, 그 얘기는 아래에서 한다.

## 늘리기: 도구를 쪼갠 이유

검색 재구성이 첫 대수술이었다. 레거시 게이트웨이에 묶여 있던 검색·조회 도구 9개를 제거하고 OpenAPI 검색 endpoint 기반의 도메인 분리 검색 6개를 신설했다(27에서 32). 핵심은 도메인 분리라는 형태다. 검색 API는 게시물 타입을 숫자 코드로 받는다. 92가 업무, 93이 일정 같은 식인데, 이 코드를 LLM에게 노출하면 "업무 찾아줘"라는 요청마다 모델이 코드 매핑을 추론해야 한다. 대신 타입 코드를 전략 내부에 고정한 도구를 타입별로 하나씩 깎았다. 추상 베이스 전략 하나를 6개 하위가 상속하면서 코드 상수와 intent, 딱 2줄만 다르다. LLM은 코드를 모른 채 도메인 의도만 매칭하면 된다.

그런데 그다음 추가한 프로젝트 게시물 목록 도구가 이 철학을 깼다. 범용 도구 하나가 타입 코드를 입력 스키마에 그대로 노출해서 "업무 목록 보여줘"에 모델이 코드를 직접 채워야 했다. 검색과 조회가 반대 철학으로 움직이는 비대칭. 그래서 범용 도구를 제거하고 타입 코드를 내부 고정한 도메인별 조회 도구 5개로 분리했다(32에서 36).

이 작업에서 값진 발견이 하나 나왔다. **검색 API와 목록 API는 타입 코드 처리가 다르다.** 검색은 인덱싱 시점에 신코드로 정규화되지만 목록은 DB를 직접 읽어 레코드가 저장된 시점의 코드를 그대로 반환한다. 옛 레코드는 구코드로 저장돼 있다. 레거시 WAS의 타입 매핑 로직이 대표 코드 하나를 신코드와 구코드의 OR 조건으로 확장해 주는데, 친절하게 신·구 코드를 둘 다 보내면 오히려 매핑 lookup이 깨져 필터가 통째로 무력화된다. 단일 대표 코드만 보내야 구코드 레코드까지 누락 없이 온다. 10년 넘은 제품의 API를 래핑한다는 건 이런 지층을 하나씩 파 보는 일이었다.

## 줄이기: 16종을 3종으로

48개 스냅샷을 찍은 뒤에도 카탈로그는 계속 자라 등록 도구가 60개에 달했다. 그리고 여기서 방향을 꺾었다.

문제는 과세분화였다. 검색 도구 6개는 literally 같은 입력 스키마 객체를 import하고 전략의 코드 상수 하나만 달랐다. 목록 5종도 같은 패턴. API가 세분화돼 있으니 도구도 따라 세분화된 결과인데, 도구가 많아지면서 세 가지가 동시에 나빠졌다. 비슷한 검색 7개 중에서 고르느라 LLM 선택 정확도가 흔들리고, tools/list의 컨텍스트 토큰이 붇고, near-duplicate 코드의 유지보수가 늘었다.

그래서 ADR을 쓰고 통합했다. 입력 스키마와 API 계약이 동일한 3개 클러스터, 검색 6종·프로젝트 목록 5종·업무수정 5종 합계 16종을 각각 1개로 병합해 등록 도구 60개를 47개로 줄였다. 설계 포인트는 두 가지다.

첫째, **discriminator는 required enum으로 강제했다.** 전부 합쳐 놓고 모든 필드를 optional로 풀고 프롬프트로 통제하는 방식은 거부했다. 스키마가 self-documenting하지 않으면 잘못된 필드 조합이 런타임에야 드러난다. 모델에게는 "어느 타입인지 명시적으로 골라라"라고 스키마 레벨에서 요구하는 게 맞다.

둘째, **병합 방식은 클러스터마다 달랐다.** 검색과 목록은 한 endpoint에 쿼리 코드 하나 차이라 enum이 코드를 고르면 끝나는 무손실 병합이었다. 반면 업무수정은 상태·담당자·우선순위·시작일·종료일이 각자 다른 PATCH endpoint로 갈라져 있어 한 요청으로 합칠 수 없었다. 단일 도구 표면 뒤에서 여러 전략을 순차 dispatch하고 부분 실패를 updated와 failed로 나눠 보고하는 composite 방식을 썼다. "비슷한 도구 묶기"로 뭉뚱그리면 안 된다. **병합 가능성은 API 계약의 동질성이 결정한다.**

정직하게 적자면 이 통합은 두 달 전 분리 결정의 역방향이다. 그땐 "타입별로 쪼개면 LLM이 명확히 고른다"가 가설이었고 실제로 코드 비노출이라는 수확도 있었다. 하지만 도구 수 폭증의 비용이 더 컸다. 같은 목표(LLM의 명확한 선택)를 이번엔 개수 압축과 명시적 discriminator로 달성했다. 현재 공개 카탈로그의 `flow_search`, `flow_list_project_items`, `flow_update_task`가 이 통합의 결과물이다.

## 사건 둘

**키 Resolver가 회사 전체 키를 날린 날.** 운영에서 일정 조회 한 번에 어느 회사의 MCP 키 전체가 일괄 revoke되는 사고가 났다. 원인은 키 조회 쿼리. "회사당 OpenAPI 키는 1개"라는 가정 아래 정렬 조건 없는 findFirst로 조회했는데, 실제 운영 DB에는 회사당 키가 N개였다. 봇별·용도별 다발급이 정상 운영 패턴이었던 것. DB가 임의로 골라준 행이 하필 무효 키였고 401을 받은 Layer 3가 설계대로 성실하게 일괄 revoke를 실행했다. 안전망 자체는 정확히 동작했다. 틀린 건 가정이었다. 수정은 등록 시각 내림차순으로 최신 키를 결정적으로 선택하게 하고, 최종 실패 메시지를 원인(OpenAPI 키 무효, 관리자 문의)과 결과(MCP 키도 revoke됨, 재발급 필요)로 분리해 LLM이 사용자에게 다음 행동을 안내할 수 있게 한 것. 후일담이 있다. 이 정교한 키 조회 인프라는 한 달 뒤 단일 마스터키와 사용자 위임 헤더 방식으로 전환되면서 캐시, single-flight, 음성 캐싱, 401 자가치유까지 통째로 소멸했다. 테넌트 격리는 정식 API 서버가 최종 강제하는 것으로 경계가 이동했다. 열심히 만든 것을 지우는 게 아까웠지만 도메인 경계가 바로잡히는 방향이라 미련 없이 걷어냈다.

**도구 개수는 사실 두 개다.** 채팅 도구 3종을 추가하다가 발견한 건데, "도구 N개"라는 숫자가 코드베이스 안에서 두 기준으로 갈라져 있었다. 항상 등록되는 정적 배열 기준의 수와 scope 게이팅 도구(생성형 이미지처럼 권한 있는 세션에만 노출)까지 포함한 노출 총합. 주석과 커밋 메시지가 두 기준을 오가며 숫자를 적는 바람에 어긋남이 누적됐다. 이 글의 연대기 숫자들이 자잘하게 출렁이는 것도 같은 이유다. 교훈은 단순하다. **개수를 적을 땐 기준을 같이 적어라.** 테스트가 강제하는 assert는 정확했고 테스트가 강제하지 못하는 주석만 거짓말을 했다.

## 도구 굵기는 LLM의 눈으로 정한다

카탈로그 진화 전체를 관통한 기준은 하나였다. API를 1:1로 래핑하는 것은 도구 설계가 아니다. 도구의 사용자는 사람이 아니라 LLM이고 굵기의 기준도 LLM의 눈이어야 한다.

- **쪼갤 때의 기준:** 모델이 내부 코드 체계를 몰라도 도메인 의도만으로 고를 수 있는가. 타입 코드를 입력으로 노출하는 도구는 그 시험을 통과하지 못해 쪼개졌다.
- **합칠 때의 기준:** 계약이 동일한가. 스키마가 같고 코드 상수 하나만 다른 도구들은 required enum 하나로 합쳐졌고 endpoint가 갈라진 도구들은 composite dispatch로 합쳐졌다.
- **개수는 목표가 아니라 결과다.** 11도 48도 47도 목표였던 적이 없다. 각 시점에 LLM의 선택 정확도와 컨텍스트 비용과 유지보수 비용의 균형점을 찾은 결과가 그 숫자였을 뿐이다.

3편에서 "상한은 hard limit이 아니라 모니터링 가이드로만 둔다"고 적었는데, 이 편의 진화가 그 문장의 실전판이었다. 벤치마크의 숫자가 아니라 우리 카탈로그의 실측과 사용감이 늘리고 쪼개고 합치는 시점을 정했다.

## 다음 편: OAuth 2.1이라는 관문

카탈로그가 자라는 동안 다른 전선이 열리고 있었다. ChatGPT와 Claude에 공식 커넥터로 제출하려면 API 키로는 부족했다. OAuth 2.1이라는 관문. 다음 편은 그 인증 아키텍처를 결정하기까지다.
