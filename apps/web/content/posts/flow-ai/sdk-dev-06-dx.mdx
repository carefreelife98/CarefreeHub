## 구조가 좋다는 것과 쓰고 싶다는 것

5편은 이렇게 끝났다. AWS SDK를 해부해서 계층 구조를 확정했고 구조는 좋았다. 그런데 구조가 좋다는 것과 쓰고 싶다는 것은 다른 문제다. 이번 편은 그 간극, 개발자 경험이 설계를 이끈 이야기다.

전환점은 문서가 아니라 질문 하나였다. "이 라이브러리의 첫 소비자는 누구인가." 그때까지의 문서들은 전부 기존 세 서비스의 중복을 청소하는 프레임 위에 있었다. 그런데 정작 가장 절실한 소비자는 기존 서비스가 아니었다. 아직 코드가 0줄인 신규 서비스들이었다. 코드가 0줄이면 절감할 중복도 0줄이다. LOC 프레임으로 계산하면 이들에게 SDK의 가치는 0이다. 2편에서 LOC 절감이 환상이라는 걸 실측으로 확인하고도 프레임 자체는 여전히 "청소"에 머물러 있었다.

그래서 프레임을 갈아끼웠다. 이건 과거의 중복을 청소하는 프로젝트가 아니었다. 앞으로 생길 N개의 서비스가 플랫폼에 붙는다. 그 비용을 영구히 0에 가깝게 만드는 프로젝트다. 목표는 AWS나 Stripe의 SDK처럼 install, configure, call 세 동작으로 끝나는 진입로다. 중복 제거는 그 결과로 따라오는 부산물이다. 프레임이 바뀌자 설계의 우선순위가 전부 다시 줄을 섰다. 기준은 하나가 됐다. **신규 서비스 개발자가 첫 호출을 쓰기까지의 거리.**

## Before: 첫 호출까지의 거리

그 거리를 실측했다. 오늘 신규 서비스가 SDK 없이 레거시 WAS의 업무 생성 API를 호출하려면 무엇을 알아야 하는가.

먼저 인증 헤더 세 개의 조립법을 기존 저장소에서 역설계해야 한다. 마스터 키는 어떤 헤더에 싣는지, 위임 대상 사용자는 어떤 헤더인지, 감사 태그는 무엇인지. 다음은 요청과 응답의 스키마다. 원본 서버는 타입을 공개 패키지로 내보낸 적이 없으므로 원본 저장소의 스키마 파일을 열어 손으로 베낀다. 3편에서 검거한 손-거울, 한 저장소가 이미 수천 줄 규모로 하고 있던 그 노동을 세 번째로 반복한다. 그다음은 봉투다. 응답 봉투 규약이 API 계열마다 다르므로 어떤 API가 어떤 봉투인지 알아야 한다. 성공 판정 기준이 HTTP 상태가 아닌 본문 안의 매직 문자열이라는 것도 외워야 한다. 마지막으로 에러의 의미는 한국어 메시지 부분 문자열로 분기한다.

개념 코드로 옮기면 이렇다.

```ts
// (개념 코드) SDK 이전: 신규 서비스가 직접 호출하는 경우
const headers = {
  "legacy-api-key": process.env.LEGACY_MASTER_KEY, // 1. 헤더 조립법을 역설계
  "acting-user-id": actor.userId, //    이게 어떤 ID인지 확인 필요
  "caller-id": "new-service",
};

// 2. 원본 서버의 스키마를 손으로 베낀다 (Last synced: ...)
const res = await fetch(`${BASE}/tasks`, {
  method: "POST",
  headers,
  body: JSON.stringify(input),
});
const json = await res.json();

if (json.resultCode !== SUCCESS_SENTINEL) { // 3. 특정 문자열 코드가 성공이라는 매직을 외운다
  if (json.errorMessage?.includes("플랜")) { // 4. 한국어 문자열로 의미 분기
    throw new Error("plan"); //    상류 카피 한 글자에 무너지는 코드
  }
  throw new Error(json.errorMessage);
}
const task = json.responseData; // 타입은 unknown
```

이걸 도메인마다, 봉투마다 반복한다. 결과적으로 비즈니스 로직의 첫 줄을 쓰기까지 수일의 내부 프로토콜 역설계가 선행된다. 원본이 필드 하나를 바꾸면 컴파일 에러 대신 프로덕션 400으로 통보받는 영구 손-동기화 부채도 함께 태어난다.

## After: 여섯 줄

SDK가 있는 세계는 이렇다. 설치 한 줄, 프로세스당 한 번의 설정 여섯 줄, 그리고 호출.

```ts
// (개념 코드) 1. install: pnpm add 한 줄
// 2. configure: 프로세스당 1회
import { PlatformClient } from "repattern-sdk";

export const platform = new PlatformClient({
  serviceToken: process.env.PLATFORM_SERVICE_TOKEN, // 단 하나의 시크릿
  callerId: "new-service", // 감사 태그
});

// 3. call: 위임 대상을 바인딩하고, 비즈니스 입력만 넘긴다
const p = platform.onBehalfOf({ userId, companyId });
const task = await p.task.create({ projectId, title: "첫 업무" });
// CreateTaskInput in, Task out. 헤더 0개, 봉투 0개, 매직 문자열 0개.
```

차이의 본질은 코드 양이 아니다. **개발자가 알아야 하는 내부 지식의 수가 N에서 0이 된다.** 헤더 이름 0개, 봉투 종류 0개, 성공 센티널 0개, 한국어 문자열 0개. 그리고 원본이 필드를 바꾸면 패키지를 올리고 컴파일하는 순간, 정확히 깨진 줄에 빨간 줄이 뜬다. 조용한 프로덕션 400이 시끄러운 컴파일 에러로 바뀐다. 2편에서 세운 correctness 정당화가 DX의 언어로 번역되면 정확히 이 문장이 된다.

## DX가 강제한 설계 결정들

"첫 호출까지의 거리"를 기준으로 삼자 설계 결정 여러 개가 이 기준에서 역산으로 강제됐다.

에러 taxonomy부터 손봤다. 개발자가 SDK를 진짜로 평가하는 순간은 성공 경로가 아니라 첫 에러를 만나는 순간이다. 에러를 만나는 순간이 DX의 반이다. 그래서 모든 실패를 단일 에러 타입으로 수렴시켰다. 안정된 영어 코드와 재시도 가능 여부를 함께 담은 타입이다. NOT_FOUND와 PERMISSION_DENIED를 구분할 수 있고 한국어 메시지로 분기하는 코드는 소비자 쪽에서 사멸한다. 한국어 메시지를 코드로 번역하는 테이블은 SDK 안에 단 한 번만 존재한다. 다만 정직하게 적어두면 이 테이블은 중복을 없앨 뿐 취약성 자체를 없애지는 못한다. 상류가 메시지 카피를 바꾸면 매핑은 여전히 강등된다. 근본 해소는 상류가 안정된 오류 코드를 내려주는 producer 변경이 선행돼야 한다. 그전까지는 매핑 테이블을 상류 메시지 정의에 대한 계약 테스트로 묶어 카피 변경이 프로덕션 대신 CI에서 터지게 만들었다.

**위임은 타입으로 강제했다.** 위임 대상 사용자를 매 호출의 마지막 인자로 받는 설계는 기각했다. 마지막 인자는 모든 호출에서 조용히 빠뜨릴 수 있는 인자이기 때문이다. 도메인 메서드는 onBehalfOf가 돌려준 객체를 통해서만 닿을 수 있게 했다. 그러면 "위임 대상을 빠뜨리는 버그"가 런타임 버그가 아니라 컴파일 에러가 된다.

**마지막은 파일 구조였다.** 도메인 파일들이 비대해져서 구조 분리가 필요해졌을 때, 독립적으로 설계한 후보 3안을 만들고 세 개의 렌즈로 교차 심사했다. 유지보수하는 사람, 소비하는 사람, 그리고 이 골격을 복제할 형제 패키지. 리소스 모듈 구조, 오퍼레이션 파일 우선 구조, 종류별 레이어 분리 구조가 후보였다. 레이어 분리안은 심사에서 가장 크게 밀렸다. 탈락 사유가 정확히 DX의 언어였다. 오퍼레이션 하나의 전모가 어느 파일에도 없다. 코드를 읽는 사람은 호출 하나를 이해하려고 파일 네 개를 순회해야 한다. 표면이 아무리 깔끔해도 그런 구조는 경험이 나쁘다. 채택안은 리소스 모듈 구조에 오퍼레이션 파일 입자를 흡수한 하이브리드였다. 오퍼레이션 파일 하나가 wire 계약 하나의 단일 진실이 되고 1,104줄짜리 진입 파일은 103줄 배럴이 됐다. 이행은 move-only 커밋 열여섯 개로 쪼갰다. 레거시 계약의 유일한 기록인 실측 주석 133라인은 라인 단위 검증기로 전량 보존을 확인했다.

## 사내에 파는 일

만들었다고 끝이 아니었다. 어느 시점에 SDK는 11개 도메인 40개 메서드, 테스트 314개 규모가 됐다. 그런데 사내 인지도는 사실상 0이었다. 잠재 소비자들은 여전히 자기 호출 계층을 손으로 만들고 있었다. 구조 정본 문서와 설치 안내는 있었지만 "왜 써야 하는가"를 30초 안에 전달하는 표면이 없었다. 그래서 소개 문서를 썼다. developer advocacy의 교훈 세 개는 그 과정에서 나왔다.

**Before는 반드시 실제 코드에서 가져온다.** 가상의 나쁜 코드를 지어내면 설득력이 죽는다. 기존 저장소의 실제 구현을 그대로 인용하니 "오퍼레이션 하나에 파일 세 개"라는 비용이 설명 없이 전달됐다.

**불리한 사실을 숨기지 않는다.** 당시 registry 발행본이 최근 도메인 전환분을 아직 포함하지 못한다는 사실을 문서에 그대로 명시했다. 홍보 문서가 한 번이라도 거짓이면 다음부터 아무도 읽지 않는다.

**홍보 수치일수록 재검증한다.** 설득의 근거가 실측이라면 그 실측이 틀리는 순간 설득 전체가 무너진다. 손-거울 규모를 합산하다가 포함 관계에 있는 두 수치를 따로 더하는 중복 계상을 저질렀고 재측정으로 정정한 뒤에야 문서에 실었다.

돌아보면 이 세 개는 4편에서 만든 trust-ledger의 원칙과 같다. 주장의 신뢰는 검증에서 나온다. 검증되지 않은 유리한 문장은 부채다. 코드를 파는 문서에도 같은 규율이 적용될 뿐이다.

## 다음 편: DX의 약속을 지키는 계약

install, configure, call. 여섯 줄의 경험은 섰다. 그런데 이 경험의 핵심 약속, "원본이 바뀌면 컴파일 에러가 정확한 줄을 가리킨다"는 SDK 혼자서는 지킬 수 없는 약속이다. producer와 소비자가 서로 다른 타입 사본을 들고 있는 한 빨간 줄은 뜨지 않는다. DX의 약속은 계약이 지켜줘야 한다. producer와 소비자가 물리적으로 같은 스키마 객체를 쓰게 만든 contract 패키지, 그리고 그 결정이 강제한 zod v4 원자 이행. 다음 편이다.
