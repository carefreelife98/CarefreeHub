## 약속은 섰는데, 보증인이 없다

6편은 이렇게 끝났다. install, configure, call. 여섯 줄의 경험은 섰고, 그 경험의 핵심 약속은 "원본이 바뀌면 컴파일 에러가 정확한 줄을 가리킨다"였다. 그런데 이 약속을 조금만 눌러보면 SDK 혼자서는 지킬 수 없는 약속이라는 게 드러난다. producer가 자기 저장소 안에 스키마를 갖고 있고, SDK가 그 스키마를 베낀 사본을 갖고 있다면, 그 사본이 아무리 정성스러워도 둘은 별개의 타입이다. producer가 필드를 바꿔도 SDK 쪽 컴파일러는 아무것도 모른다. 빨간 줄은 두 벌의 타입이 물리적으로 같은 하나일 때만 뜬다.

실태를 실측하니 더 나빴다. 요청 스키마는 게이트웨이 안에 있었지만, **응답 계약은 어디에도 없었다.** 응답을 조립하는 매퍼들은 전부 익명 리터럴을 반환하고 있었고, 이름 붙은 반환 타입은 0건이었다. 그래서 소비자들은 응답 모양을 손으로 베끼고 있었다. 한 소비자 서비스에서만 수십 개 파일, 천 줄이 넘는 손-거울이 나왔다. 3편에서 검거했던 그 패턴이 층을 바꿔 게이트웨이 표면에서 다시 자라고 있었던 것이다. 소비자가 늘 때마다 이 비용은 비례해서 반복된다.

## contract 패키지: 스펙 생성보다 강한 것

표준적인 처방은 스펙이다. OpenAPI 문서를 정본으로 세우고, 스펙에서 SDK를 생성하고, 서버 구현이 스펙과 어긋나는지 대조 테스트를 돌린다. 실제로 5편의 리서치에서 확인한 대로 OpenAI와 Cloudflare의 공식 SDK가 이 경로다. 그런데 이 경로에는 태생적인 틈이 있다. 스펙과 구현이 **두 벌**이라는 것. 생성과 대조는 두 벌이 어긋나는 것을 빨리 잡는 장치이지, 어긋남 자체를 없애는 장치가 아니다.

같은 저장소 생태계, 같은 언어, 같은 런타임이라는 우리 조건에서는 더 강한 수가 가능했다. **계약을 별도 패키지로 꺼내고, producer와 클라이언트가 물리적으로 같은 스키마 객체를 import하는 것.** 게이트웨이는 이 객체로 요청을 검증하고 응답을 parse하며, 클라이언트는 같은 객체에서 타입과 런타임 검증을 얻는다. 어긋날 두 벌 자체가 존재하지 않는다.

```ts
// (개념 코드) 계약 패키지의 오퍼레이션 파일 하나
export const createTask = defineContract({
  method: "POST",
  path: "/tasks",
  scope: "task:write",
  request: CreateTaskInput, // zod 스키마
  response: Task, // zod 스키마
});
// producer: createTask.request 로 검증, createTask.response 로 응답 parse
// 클라이언트: 같은 객체에서 타입 추론 + 런타임 검증. 오퍼레이션당 본문 4줄
```

이게 사파의 발명이 아니라는 것도 확인했다. contract-first 진영에서는 오히려 이쪽이 기본값이다. gRPC 공식 튜토리얼은 생성된 계약을 "서버가 구현해야 할 인터페이스 타입"이라고 부르고, ConnectRPC는 서비스 구현체에 계약이 만든 타입을 강제하며, AWS의 Smithy는 model, client, server 세 갈래가 하나의 모델에서 파생되는 구조를 표준으로 못박는다. 서버가 타 패키지에 정의된 계약을 구현하는 것. 우리는 그 패턴을 코드 생성기 없이 zod 객체 공유로 얻은 셈이다. OpenAPI 스펙은 버리지 않는다. 다만 지위가 바뀐다. 스펙이 정본이고 코드가 파생물인 게 아니라, **계약 코드가 정본이고 스펙은 외부 문서와 타 언어 소비자를 위한 파생 산출물**이다.

비용도 정직하게 계산했다. 계약이 별도 패키지가 되면 계약 변경마다 패키지 버전을 올리고 발행하는 릴리스 커플링이 생긴다. 우리는 이것을 감수한 게 아니라 **원해서 골랐다.** 공개 계약의 변경이 커밋 로그 속에 묻히는 대신, semver bump라는 명시적 사건이 되기 때문이다. 계약을 바꾸는 일은 마찰이 있어야 정상이다. 의도된 마찰이다.

## 그 결정의 대가: 점진 이행이라는 선택지의 소멸

결정에는 청구서가 따라왔다. 계약 패키지의 전제가 "물리적으로 같은 zod 객체"라는 말은, zod의 버전이 더 이상 각 패키지가 알아서 고르는 의존성이 아니라 **계약 경계 전체가 공유하는 단일 축**이 됐다는 뜻이다. 그 상태에서 zod v4 이행이 도마에 올랐다.

v3와 v4는 스키마 객체가 상호 비호환이다. v3 스키마를 v4 파서에 넣을 수 없다. 보통의 모노레포라면 패키지 하나씩 올리면 되지만, 우리는 그 길을 스스로 막아둔 상태였다. 계약 경계를 반쯤 넘긴 중간 상태, 예컨대 contract만 v4인 상태는 한 프로세스 안에 zod 인스턴스 두 개를 만든다. 이건 이론상의 걱정이 아니었다. 이중 인스턴스는 이미 한 번 실제로 발화한 실패 모드였다. 다른 인스턴스가 던진 에러는 `instanceof ZodError` 판정을 통과하지 못하고, 검증 실패로 처리됐어야 할 400이 정체불명의 500으로 누출됐다.

그래서 결론은 하나로 좁혀졌다. **계약 경계가 곧 이행 단위다.** 계약, 공통 코어, 게이트웨이 클라이언트 세 패키지와 producer의 검증 진입점까지를 하나의 릴리스 트레인으로 묶어 동시에 넘긴다. 원자 이행. 계약 패키지 결정이 이행 전략의 자유도를 없앤 것이지만, 뒤집어 보면 계약 결정이 이행 단위까지 정확하게 규정해 준 것이기도 하다.

위험은 컴파일러가 못 잡는 곳에 있었다. v4는 모르는 옵션을 예외 없이 무시한다. v3에서 쓰던 메시지 옵션들은 제거됐는데, 그걸 그대로 두면 타입체크도 빌드도 통과한 채 **사용자에게 나가는 문구만 영어 기본값으로 통째로 바뀐다.** 그리고 그 400 응답 문구는 이미 외부가 의존하는 공개 표면이었다. 문구가 바뀌면 개선이 아니라 계약 파기다.

## 이행 실전: 가드를 먼저 세운다

그래서 순서를 뒤집었다. 코드를 고치기 전에 가드부터 세웠다.

**공개 문구 스냅샷 13건.** 메시지 빌더의 반환값이 아니라 소비자가 실제로 받는 최종 문자열을 브랜드 2종에 대해 스냅샷으로 박제했다. 여기에 같은 검증 상황을 v3 스키마와 v4 스키마로 각각 돌려 문자 단위 동일을 단언하는 등가성 테스트를 더했고, 이 게이트 통과를 본이행 착수 조건으로 걸었다. 테스트 자체의 유효성도 실증했다. 에러 매핑 키를 v4 형태로 바꿔 넣으면 9건이 실제로 red로 떨어지는지 먼저 확인한 것이다. 안 깨지는 가드는 가드가 아니다.

가드가 서자 함정이 하나 잡혔다. v4는 enum의 오값과 필수값 누락을 **둘 다 같은 issue 코드로** 보낸다. 기계적으로 rename만 하면 필수값을 빠뜨린 사용자에게 enum 오값 문구가 나간다. 입력이 undefined인지로 분기해 누락 문구를 보존했다.

```ts
// (개념 코드) v4는 오값과 누락을 같은 코드로 합쳤다
if (issue.code === "invalid_value" && issue.input === undefined) {
  return REQUIRED_FIELD_MESSAGE; // 누락에는 누락 문구를
}
```

**철회한 우회도 있었다.** v4에서 사라진 API 탓에 수백 곳의 스키마 선언을 고치는 대신, 전역 설정으로 커스텀 에러 맵을 한 번에 꽂는 방법을 한 번 썼다. 돌아서서 이건 우회라고 판정하고 되돌렸다. 전역 설정은 누가 언제 어떤 문구 사전을 공급하는지가 호출부에서 보이지 않는다. 되돌린 뒤에는 실측부터 했다. producer의 zod parse 진입점을 전수 조사하니 실제로는 **2곳뿐**이었다. 나머지 parse처럼 보이던 호출들은 전부 JSON.parse였다. 진입점 2곳에 에러 맵을 인자로 명시 주입하는 것으로 끝났다. 전역 상태 0. 366곳을 고치기 싫다는 공포가 만든 우회였는데, 실측하니 애초에 2곳짜리 문제였던 것이다.

**응답 스키마는 strip으로 정했다.** strict는 producer가 응답에 키 하나만 추가해도 모든 소비자에게서 throw가 터진다. passthrough는 타입에 없는 유령 필드를 통과시키고 오타 검출력까지 떨어뜨린다. strip은 정확히 원하는 의미를 준다. **producer가 키를 추가해도, 계약을 갱신하기 전의 클라이언트는 그 키를 못 받는 것이 정상이다.** 새 필드를 받는 유일한 길은 계약 패키지 버전을 올리는 것. 앞서 수용한 의도된 마찰과 같은 원칙이 응답 방향에도 적용된 셈이다. producer 자신이 역추출 누락을 fail-fast로 잡는 데 필요한 strict 검증은 계약이 파생 스키마로 따로 제공해서, 소비자 표면과 분리했다.

마지막 함정은 코드 밖에 있었다. 첫 발행이 부분 실패했다. 세 패키지 중 둘은 올라갔는데 하나만 타입 선언을 못 찾고 죽었다. 원인은 발행 도구가 패키지들을 **병렬로** 발행하는데, 각 패키지의 prepublishOnly 훅이 clean과 build를 다시 돌렸기 때문이다. 한 패키지의 dist 삭제가, 다른 패키지가 그 타입을 읽으며 빌드하는 도중에 끼어든 것이다. prepublishOnly를 세 패키지 모두에서 제거하고, 빌드는 릴리스 스크립트가 토폴로지 순서로 한 번만 하도록 바꿨다. 각자 알아서 빌드하는 편의 장치가 병렬 실행 아래에서는 경합 조건이 된다.

이행 결과는 표 한 줄로 요약된다. 세 패키지 테스트 127건 통과, producer 타입체크 무오류, zod 인스턴스 1개, 그리고 **공개 400 문구는 한 글자도 바뀌지 않았다.** 스냅샷 13건이 그걸 증명한다.

## 배운 것

계약을 문서로 두면 어긋남을 감시해야 하고, 코드로 두면 어긋남이 성립하지 않는다. 이번 편의 결정은 전부 그 한 문장의 각론이었다. 물리적 객체 공유는 감시를 불필요하게 만들었고, 그 대가로 버전 축이 묶이며 원자 이행을 강제했고, 원자 이행은 스냅샷과 등가성 테스트라는 가드를 먼저 요구했다. 결정이 다음 결정의 형태를 규정하는 연쇄. 그리고 그 연쇄의 어느 지점에서도, 지켜야 할 것의 정의는 같았다. 소비자가 관찰할 수 있는 표면은 계약이고, 계약은 깨지 않거나, 깨는 순간을 명시적 사건으로 만들거나 둘 중 하나여야 한다.

계약은 코드로 강제됐다. 남은 것은 그 코드를 소비자에게 배달하는 일이었다. 그리고 배포는 코드보다 어려웠다. 다음 편은 registry 이관과 강제 개명, 그리고 토큰의 정치학이다.
