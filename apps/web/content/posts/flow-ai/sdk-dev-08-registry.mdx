## 잘 만든 패키지가 소비자에게 닿지 않는다

7편은 이렇게 끝났다. 배포는 코드보다 어려웠다. 이번 편이 그 이야기다. contract 패키지까지 세워 타입의 단일 진실을 만들었는데, 정작 그 패키지가 소비자에게 물리적으로 배달되지 않는 문제가 터졌다.

당시 SDK는 사내망 전용 사설 registry(Verdaccio)로 발행되고 있었다. 사내망 안에서는 아무 문제가 없다. 그런데 첫 실소비자가 될 MCP 서버 레포의 CI는 GitHub-hosted 러너에서 돈다. 러너는 공개 인터넷에 있고, 사내 registry는 내부망에서만 닿는다. 결과는 설치 단계의 소켓 타임아웃. 패키지 품질과 무관하게, CI가 install에서 죽는 SDK는 소비자 입장에서 존재하지 않는 것과 같다.

이 문제의 고약한 점은 비대칭이라는 것이었다. SDK 레포 자신의 CI는 멀쩡했다. 워크스페이스 내부 의존이 workspace 프로토콜로 링크돼 registry를 아예 치지 않기 때문이다. 만든 쪽의 초록불이 쓰는 쪽의 초록불을 보장하지 않는다는 것, 이 비대칭이 원인 파악을 늦췄다.

선택지는 다섯이었다. 사내망에 self-hosted 러너를 띄우는 안은 러너 인프라 운영 부담으로, 소비자 CI가 SDK 소스를 직접 빌드하는 안은 발행이라는 개념 자체를 무의미하게 만들어서, 사내 registry를 외부에 개방하는 안은 보안 때문에 기각했다. 남은 것은 GitHub Packages 이관이었다. 러너와 registry가 같은 인프라 위에 있으니 접근성 문제가 뿌리부터 사라진다.

## scope는 GitHub 조직명을 따른다

그런데 GitHub Packages에는 다른 registry에 없는 제약이 하나 있다. npm scope를 GitHub 계정 이름으로 그대로 라우팅한다는 것이다. `@repattern/core`를 발행하려면 `repattern`이라는 GitHub 조직을 소유해야 한다.

그리고 `repattern` 조직은 실재했고, 우리 것이 아니었다. RePattern이라는 독일 회사(repattern.de)가 2022년부터 쓰고 있는 이름이었다. 활동 중인 회사의 조직명이니 양도 요청도 선택지가 아니다. 1편에서 붙인 이름이 3년 먼저 등록된 이름과 충돌한 것뿐이고, 누구의 잘못도 아니다. 다만 결론은 하나였다. GitHub Packages로 가려면 scope를 버려야 한다.

여기서 함정 하나. **이 충돌은 `npm publish --dry-run`으로는 검증되지 않는다.** dry-run은 registry를 치지 않기 때문이다. 로컬에서 dry-run이 통과하는 것을 보고 "되겠네"라고 판단했다면 실제 발행에서야 벽을 만났을 것이다. 인증 토큰으로 registry에 직접 GET을 날려 실측했고, 응답이 제약을 정확히 말해줬다. `@repattern/flow`를 조회하면 owner가 `repattern`인 패키지가 없다는 404가 온다. scope가 소유자 이름으로 해석되고 있다는 증거다. 4편의 trust-ledger에 적었던 원칙 그대로다. 사실은 도구가 아니라 실측으로 검증한다.

개명은 회사 GitHub 조직명 스코프로 갔다. `@repattern/core`가 조직명 스코프 아래 `repattern-core`가 되는 식으로, 프로젝트 정체성은 패키지명 접두어로 살렸다. alias로 옛 이름을 유지하는 절충안도 검토했지만 lockfile에 간접층이 생겨 기각했다. 이관하면서 지킨 원칙이 둘 있다. 첫째, 버전은 승계한다. 코드가 한 줄도 안 바뀌었는데 이름이 바뀌었다고 버전을 올리면 구 이름과 신 이름의 대응이 깨진다. 둘째, 히스토리 문서는 고치지 않는다. CHANGELOG의 과거 항목은 "그 시점에 그 이름으로 발행했다"는 사실의 기록이다. 지금 이름으로 일괄 치환하면 없던 역사를 만드는 것이다.

## 초록 로그는 결과의 증거가 아니다

이관 발행 자체는 성공했다. 테스트 688개 통과, tarball을 실제로 만들어 별도 프로젝트에서 설치와 타입체크와 런타임 로드까지 확인한 뒤였다. 그런데 발행 후 확인해 보니 **git 태그가 하나도 없었다.** 릴리스마다 태그를 만드는 changesets가 로그에는 태그 다섯 개를 만들었다고 찍어놓고, 실제로는 0개였다.

원인은 changesets 내부의 이 함수다.

```js
// @changesets/git 의 tag() (요지)
async function tag(tagStr, cwd) {
  const gitCmd = await spawn("git", ["tag", tagStr, "-m", tagStr], { cwd });
  return gitCmd.code === 0; // 호출부가 이 반환값을 버린다
}
```

성공 여부를 성실히 반환하는데 호출부가 그 값을 무시한다. `git tag`가 실패해도 `New tag: ...` 로그는 그대로 찍힌다. 뒤이은 `git push --tags`는 올릴 태그가 없으니 "Everything up-to-date"로 조용히 성공한다. 두 단계가 모두 초록인데 결과물만 없는, 교과서적인 침묵 실패다. 태그 없이 발행된 패키지는 소스 커밋으로 역추적할 수 없으니 그냥 넘어갈 수 있는 문제가 아니었다.

러너에서 git tag가 왜 실패했는지는 끝내 확정하지 못했다. changesets가 stderr를 삼켜 로그에 남지 않았기 때문이다. 첫 가설은 annotated 태그라 git identity가 필요한데 러너에 없었다는 것이었는데, identity를 비운 환경에서 재현해 보니 git이 알아서 유도해 태그가 정상 생성됐다. 가설 폐기. 재현되지 않는 가설을 원인이라고 적어두면 다음 사람이 잘못된 곳을 파게 된다. 그래서 대응은 원인 확정에 의존하지 않는 방어로 갔다. 워크플로가 태그를 직접 만들고 실패 시 즉시 죽으며, push 후에는 `git ls-remote`로 원격에 태그가 실제로 있는지 조회해서 없으면 실패시킨다. 부작용을 일으키는 단계는 로그가 아니라 **결과물 자체를 조회해서** 확인한다. 유실된 태그 다섯 개는 실제 발행 커밋 기준으로 수동 복구했다.

## 토큰의 정치학

이관으로 인증은 GitHub PAT 하나로 단일화됐다. 깔끔해 보였는데, GitHub Packages는 private 패키지의 설치에도 인증을 요구하므로 이제 모든 소비처가 이 토큰에 의존하게 됐다는 뜻이기도 했다. 그리고 곧 이 질문이 왔다. "이 PAT을 다른 담당자에게 넘기려면 뭘 고려해야 하나."

답을 찾다가 질문의 전제가 틀렸다는 것을 알았다. **PAT은 권한이 아니라 신원이다.** 토큰 문자열을 사람에게 넘기면 첫째, 새 사람의 행동이 전부 발급자의 이름으로 감사 로그에 남는다. 둘째, classic PAT의 스코프는 토큰이 아니라 계정 전체에 걸리므로, 패키지 읽기 권한 하나만 붙어 있어도 그 계정이 닿는 모든 조직의 private 패키지가 함께 열린다. 셋째, 발급자가 2FA를 재설정하는 순간 전부 죽는다. 그러니 토큰 이관이라는 것은 존재하지 않는다. 있는 것은 재발급, 교체, 폐기의 순서뿐이고, 구 토큰 폐기가 맨 마지막이어야 한다. 먼저 폐기하면 교체가 끝나기 전까지 전부 죽는다. 폐기의 증거도 버튼이 아니라 구 토큰으로 인증했을 때의 401 응답이다. 태그 사건과 같은 규율이다.

교체하려면 토큰이 어디에 박혀 있는지 전부 알아야 한다. 그래서 소비처를 전수 조사했는데, 여기서 이번 편에서 가장 뼈아픈 발견이 나왔다. **운영 정본 README가 현실과 두 군데 어긋나 있었다.** 정본은 토큰을 조직 레벨 secret으로 한 번만 두고 소비 레포들이 공유한다고 적고 있었다. 실측하니 첫째, 그 secret은 조직 secret이 아니라 특정 레포의 repo secret이었다. 둘째, "한 번"도 아니었다. 소비처는 셋이었다. CI secret, 컨테이너 빌드가 직접 읽는 빌드 호스트의 전역 npm 설정, 그리고 개발자 로컬. 의도한 설계를 정본에 적어두고 배선은 다르게 되어 있던 것이고, 문서를 현실에 맞게 고치기 전까지 아무도 그 격차를 몰랐다.

이 격차의 위험은 조용하다는 데 있다. 정본을 믿고 secret 하나만 갈면 CI는 통과한다. 실패는 한참 뒤에 빌드 호스트에서 401로 나타난다. 이관을 절반만 했다는 사실 자체를 한동안 모르는 구조다. 문서는 검증 없이 낡고, 낡은 문서는 틀린 지도보다 나쁘다. 지도가 틀렸다고 의심할 이유조차 주지 않기 때문이다.

결론은 머신 계정이었다. 사람 계정의 PAT을 다른 사람 계정의 PAT으로 바꾸는 것은 문제를 다음 인사이동까지 미루는 것뿐이다. 조직 소유의 머신 계정으로 발급하면 소유권이 조직에 남아 사람의 이동과 무관해지고, 기존 배선을 한 글자도 바꿀 필요가 없다. 토큰 자동 회전이 되는 GitHub App도 검토했지만, CI 밖의 소비처가 존재하는 한 토큰 생성 단계가 추가되는 비용이 이점을 상쇄했다.

## 배포 인프라도 계약이다

7편에서 producer와 소비자 사이의 타입 계약을 세웠다. 이번 편에서 배운 것은 그 아래층에도 같은 원리가 적용된다는 것이다. registry 접근성, 발행 태그, 토큰의 소유권, 이것들도 전부 producer와 소비자 사이의 계약이다. 그리고 계약의 신뢰는 문서가 아니라 검증에서 나온다. dry-run이 아니라 인증 GET으로, 발행 로그가 아니라 태그 조회로, README가 아니라 소비처 전수로. 이번 편의 사고 세 건은 전부 "문서나 로그를 믿고 결과물을 조회하지 않은" 같은 모양의 실패였고, 대응도 전부 같은 모양이었다. 결과물을 직접 조회하는 검증을 파이프라인에 박는 것.

배달 경로는 안정됐다. 이제 1.0을 붙일 차례라고 생각했다. 승격 감사를 돌려보기 전까지는. 마지막 편은 스스로 내린 1.0 불가 판정, 그리고 첫 실소비자의 이야기다.
