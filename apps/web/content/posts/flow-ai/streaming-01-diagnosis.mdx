## 팬이 돌기 시작했다

2025년 10월 말, AI 채팅 기능을 쓰다가 이상한 걸 느꼈다. 질문 하나를 던지고 긴 응답이 스트리밍되는 동안 노트북 팬이 돌기 시작한 것이다. 동영상 편집을 하는 것도, 빌드를 돌리는 것도 아니었다. 그냥 텍스트가 화면에 흘러나오고 있을 뿐인데.

Chrome Performance Monitor를 열어놓고 다시 재현해봤다. 스트리밍이 시작되면 CPU 사용률이 60\~80%로 올라갔고 코드 블록과 표가 섞인 길고 복잡한 응답에서는 90%까지 치솟았다. 프레임은 20\~30 FPS로 떨어져 스크롤이 눈에 띄게 끊겼다. 응답이 길어질수록 증상은 심해졌다. 사용자 입장에서는 "AI가 답을 쓰는 동안 브라우저가 버벅인다"는 체감이고 저사양 기기라면 브라우저 프리징까지 갈 수 있는 수치였다.

백엔드가 본업이라 처음엔 서버 쪽을 의심했다. 토큰을 너무 잘게 쪼개 보내나? 이벤트가 너무 잦나? 하지만 네트워크 탭은 평온했다. 문제는 토큰을 받은 다음, 브라우저 안에서 벌어지고 있었다.

## 옆 탭의 ChatGPT는 조용했다

원인을 파기 전에 비교 대상을 하나 세웠다. 같은 노트북, 같은 브라우저에서 ChatGPT에 비슷한 길이의 응답을 받아보며 Performance Monitor를 지켜봤다.

| 항목 | ChatGPT | 우리 서비스 |
| --- | --- | --- |
| CPU 사용률 | 평균 20\~30% | 60\~80%, 스파이크 시 90% |
| 렌더링 방식 | 받은 청크를 버퍼에 모아 일정 주기로 flush | SSE 이벤트 도착 즉시 렌더링 |
| 체감 | 부드러운 스트리밍 | 끊김, 팬 소음 |

같은 일을 하는데 CPU는 세 배 차이. 모델이나 서버의 문제가 아니라 **렌더링 구조의 문제라는** 뜻이었다. ChatGPT는 SSE 이벤트를 받는 족족 그리지 않는다. 입력은 실시간으로 받되 화면 갱신은 별도의 주기로 제어한다. 우리는 이벤트가 오는 대로 전부 그리고 있었다. 이 차이가 어디서 얼마나 비싸지는지를 뜯어보니 원인은 하나가 아니라 넷이었다.

## 4중 원인: 이벤트 하나가 사슬 전체를 완주한다

당시 우리 렌더링 파이프라인은 이랬다.

```
SSE 이벤트 (초당 수십~수백 회)
    ↓ 문자열 누적 (prev + chunk)
    ↓ 상태 스토어 업데이트 → 메시지 배열 전체 복사
    ↓ 메시지 컴포넌트 리렌더
    ↓ 마크다운 재파싱 (remark/rehype 플러그인 체인)
    ↓ VDOM diff → DOM 갱신 (Reflow + Repaint)
```

문제는 이 사슬을 **이벤트마다 처음부터 끝까지 한 번씩 완주한다는** 것이었다. 각 단계를 따로 보면 이렇다.

**첫째, 이벤트 루프 과부하.** SSE는 응답 하나에 수백\~수천 번의 이벤트를 발생시킨다. 이벤트마다 상태 업데이트와 DOM 갱신이 따라붙으면 Reflow와 Repaint가 초당 수십 회 누적된다. 가상 DOM 기반 렌더러는 여기에 diff 계산 비용까지 매번 얹는다.

**둘째, 문자열 누적과 GC 압력.** `setText(prev => prev + chunk)` 패턴은 이벤트마다 새 문자열 객체를 만든다. 응답이 길어질수록 복사되는 문자열도 길어지고 버려지는 이전 문자열이 쌓이면서 가비지 컬렉션 빈도가 올라간다. 스트리밍 후반부로 갈수록 더 무거워지는 구조다.

**셋째, DOM 갱신 횟수 과다.** 텍스트를 매번 갈아끼우면 브라우저는 layout → paint → composite를 매번 수행한다. 한 번은 싸지만 초당 수십 번이면 CPU가 급격히 오른다.

**넷째, React의 리렌더 구조.** 스트리밍 텍스트를 React 상태로 관리하니 이벤트마다 컴포넌트 트리 diff가 돌았다. 게다가 zustand 스토어의 메시지 업데이트가 불변성 유지를 위해 **메시지 배열 전체를 복사하고** 있었고 props가 매번 바뀌니 `memo` 최적화도 전부 무력화됐다.

넷 중 무엇 하나가 결정타라기보다, 네 비용이 한 사슬에 엮여 이벤트 빈도만큼 곱해지고 있었다. 그렇다면 첫 수는 명확하다. **사슬을 도는 횟수 자체를 줄이는 것.**

## 1차 대응: 입력은 실시간, 렌더링은 프레임 단위로

ChatGPT 방식을 그대로 가져왔다. 청크는 도착 즉시 배열 버퍼에 push만 하고 실제 렌더링은 `requestAnimationFrame`으로 예약해 프레임 단위로만 수행한다.

```typescript
const chunksBufferRef = useRef<string[]>([]);
const rafSchedulerRef = useRef<number | null>(null);

// 청크 도착: push만 하고 끝, 렌더링은 예약만
const scheduleFlush = useCallback(() => {
  if (rafSchedulerRef.current !== null) return; // 중복 예약 방지
  rafSchedulerRef.current = requestAnimationFrame(flushBuffer);
}, [flushBuffer]);

// 프레임 콜백: 쌓인 청크를 join 한 번으로 합쳐 일괄 반영
const flushBuffer = useCallback(() => {
  const buffered = chunksBufferRef.current.join("");
  accumulatedContentRef.current += buffered;
  replaceAiMessage(accumulatedContentRef.current /* ... */);
  chunksBufferRef.current = [];
  rafSchedulerRef.current = null;
}, [replaceAiMessage]);
```

배열 push → flush 시점에 `join` 한 번. 문자열 누적의 GC 문제(둘째 원인)와 이벤트당 즉시 렌더링(첫째 원인)이 이 구조 하나로 같이 줄어든다.

그런데 rAF만으로는 부족했다. rAF는 "다음 프레임에 실행"일 뿐이라 여전히 매 프레임, 즉 초당 30회 가까이 렌더링이 돌 수 있었다. 그래서 flush에 최소 간격을 강제하는 스로틀링을 더했다.

```typescript
const THROTTLE_MS = 80; // 초당 12~13회

const now = performance.now();
if (now - lastFlushTimeRef.current < THROTTLE_MS) {
  rafSchedulerRef.current = requestAnimationFrame(flushBuffer); // 재예약
  return;
}
```

80ms라는 값은 감이 아니라 튜닝의 결과다. 간격별로 CPU와 체감을 비교했다.

| 간격 | 렌더링/초 | CPU | 체감 |
| --- | --- | --- | --- |
| 60ms | 16\~17회 | 40\~45% | 매우 부드러움 |
| **80ms** | **12\~13회** | **35\~40%** | **매우 부드러움 (채택)** |
| 100ms | 10회 | 30\~35% | 부드러움 |
| 150ms | 6\~7회 | 25\~30% | 뚝뚝 끊기는 느낌 |

100ms 아래로는 사람 눈이 차이를 거의 못 느꼈고 150ms부터는 타자기가 뚝뚝 끊기는 느낌이 났다. CPU를 조금 더 쓰더라도 체감이 확실히 부드러운 80ms를 골랐다.

버퍼링을 넣는 순간 따라오는 엣지 케이스도 있었다. 스트리밍 완료·중단·에러 시에는 버퍼에 남은 청크를 **즉시 flush해야** 마지막 몇 글자가 유실되지 않고, 재시도 이벤트가 오면 버퍼를 비우고 예약된 rAF를 취소해야 이전 응답 조각이 새 응답에 섞이지 않는다. 컴포넌트 unmount 시 `cancelAnimationFrame` 정리도 빼먹으면 안 된다. 버퍼는 성능을 얻게 해주는 대신 "버퍼에 남은 것"이라는 새로운 상태를 관리할 부담을 남긴다.

결과는 분명했다. 렌더링 빈도가 초당 \~30회에서 12\~13회로 60% 줄었고 평상시 CPU는 50\~70%에서 35\~40%로 내려왔다. 팬 소음도 줄었다.

## 그래도 남은 병목

여기서 끝이면 좋았겠지만 긴 응답 후반부나 코드 블록이 많은 응답에서는 여전히 CPU가 70\~90%까지 치솟는 구간이 남아 있었다. 스로틀링은 사슬을 도는 **횟수를** 줄였을 뿐, 한 바퀴 도는 **비용은** 그대로였기 때문이다.

실마리는 스로틀링 작업 중에 했던 실험 하나에 있었다. 스트리밍 중에는 마크다운 파싱을 아예 끄고 `<pre>`로 raw 텍스트만 뿌려봤더니, 원문이 그대로 노출돼 채택은 못 했지만 파싱 비용이 사라진 만큼 CPU가 내려가는 게 눈에 보였다. 그리고 우리 파이프라인은 청크가 올 때마다 **지금까지 누적된 문서 전체를** react-markdown과 rehype 플러그인 체인에 다시 태우고 있었다. 문서가 길어질수록 flush 한 번의 비용이 선형으로 커지니 빈도를 아무리 줄여도 후반부에는 결국 치솟는 구조였다.

빈도는 잡았다. 다음은 렌더러 자체다. 다음 편에서는 "스트리밍 중에는 React를 우회한다"는, 조금 과격하게 들리는 결정을 내리게 된 이야기를 쓴다. 스트리밍 중엔 Marked.js로 HTML을 만들어 innerHTML에 직접 꽂고 응답이 끝나면 react-markdown으로 갈아타는 하이브리드 렌더러다.
