## 빈도를 잡았는데도 팬이 돈다

[지난 편](/posts/flow-ai/streaming-01-diagnosis)에서 rAF 스로틀링으로 렌더링 빈도를 초당 30회에서 12~13회로 줄였다. 평상시 CPU는 35~40%로 내려왔지만, 코드 블록과 표가 섞인 긴 응답에서는 여전히 70~90%까지 치솟는 구간이 남아 있었다. 횟수를 줄여도 한 번의 렌더가 비싸면, 문서가 길어지는 순간 다시 무너진다.

Chrome Performance로 1초 구간을 잘라 프로파일을 떠보니 범인이 선명했다. Main 스레드의 72%가 Scripting이었고, 그 안을 열어보면 ReactMarkdown 파싱, rehype-prism 코드 하이라이팅, rehype-raw HTML 처리, 그리고 VDOM diffing이 상위를 전부 차지하고 있었다. Idle은 2%. 브라우저에게 숨 쉴 틈이 없었다.

구조적으로 보면 이렇다. 스트리밍 중에는 청크가 올 때마다 **누적된 문서 전체를** 다시 파싱한다. 1,000자씩 10번 스트리밍되는 10,000자 응답이라면, 파싱 대상은 1,000 + 2,000 + … + 10,000 = 55,000자다. 문서는 한 번만 커지는데 파싱 총량은 제곱으로 자란다. 게다가 그 파싱이 react-markdown이다. remark/rehype 플러그인 체인을 통과해 VDOM을 만들고 diff까지 하는, 스트리밍 중에는 아무도 쓰지 않는 인터랙티브 컴포넌트(복사 버튼, 출처 모달, 이미지 확대)까지 매번 다시 만드는 풀코스.

여기서 질문이 갈렸다. 스트리밍 중에 그 풀코스가 필요한가? 사용자가 보는 건 흘러나오는 텍스트다. 클릭할 것도, 모달을 열 것도 없다. 필요한 건 "마크다운처럼 보이는 화면"이지 "완전한 React 트리"가 아니었다.

## 하이브리드 전략: 각 구간에 맞는 렌더러를

그래서 렌더러를 시점에 따라 갈아끼우기로 했다. 한 문장으로 요약하면 이렇다.

> 스트리밍 중에는 React를 우회하고, 완료 후에만 React로 전환한다.

- **스트리밍 중 (isStreaming=true)**: 경량 파서인 Marked.js로 마크다운을 HTML 문자열로 변환하고, `innerHTML`로 DOM에 직접 꽂는다. React는 관여하지 않는다.
- **완료 후 (isStreaming=false)**: react-markdown이 remark-gfm, rehype-raw, rehype-prism과 커스텀 컴포넌트를 갖추고 최종 렌더링을 **한 번만** 수행한다. 복사 버튼, 출처 모달, 이미지 확대 같은 인터랙션이 이때 붙는다.

렌더러 컴포넌트는 분기 하나가 전부다.

```tsx
function MarkdownRenderer({ markdownText, messageId, isStreaming }) {
  // 스트리밍 중: React children이 없는 빈 div만 렌더
  // 스트리밍 훅이 이 div의 innerHTML을 직접 갱신한다
  if (isStreaming) {
    return <div data-streaming-message={messageId} className="prose ..." />;
  }

  // 완료 후: react-markdown이 완전한 인터랙티브 트리를 1회 렌더
  return (
    <ReactMarkdown
      components={markdownComponents}
      remarkPlugins={[remarkGfm, remarkBreaks]}
      rehypePlugins={[rehypeRaw, rehypePrism]}
    >
      {markdownText}
    </ReactMarkdown>
  );
}
```

여기서 제일 조심한 지점이 **React와의 충돌이다.** React가 children을 관리하는 요소의 innerHTML을 밖에서 바꾸면, 다음 reconciliation 때 React가 원래 children으로 되돌려버린다. 그래서 스트리밍 중의 div는 children이 아예 없는 빈 껍데기로 뒀다. React 입장에서 이 div는 "비어 있는 것"이므로 innerHTML을 아무리 바꿔도 건드리지 않는다. 스트리밍이 끝나면 innerHTML 조작을 완전히 멈추고 제어권을 React에 통째로 넘긴다. 두 세계가 같은 DOM을 동시에 만지는 순간이 없도록, `isStreaming` 플래그로 렌더링 경로를 시간축에서 완전히 분리한 것이다.

스트리밍 훅 쪽은 누적 마크다운을 `useRef`에만 들고 있다가(리렌더 트리거 없음), flush 시점에 `renderMarkdown()`으로 HTML을 만들어 `data-streaming-message` 속성 셀렉터로 찾은 div에 꽂는다. 완료 이벤트가 오면 그제야 최종 텍스트로 상태를 한 번 업데이트하고 `isStreaming`을 내린다. 스트리밍 내내 React 상태 업데이트는 0회, 완료 시 1회다.

## 공짜는 아니었다: 트레이드오프 세 가지

이 구조는 성능을 주는 대신 청구서를 세 장 내밀었다.

**첫째, 같은 UI를 두 렌더러가 그린다.** Marked의 HTML과 react-markdown의 JSX가 다르게 생기면, 스트리밍이 끝나는 순간 화면이 미묘하게 바뀌는 깜빡임이 생긴다. 실제로 초기엔 같은 Tailwind 클래스 문자열이 여러 파일에 하드코딩돼 있어 한쪽만 고치는 사고가 났다. 해결은 스타일의 단일 진실 공급원. 코드 블록, 표, 헤딩, 인용 칩 등 모든 요소의 클래스 문자열을 스타일 상수 모듈 한 곳에 모으고, Marked 커스텀 렌더러와 React 컴포넌트가 같은 상수를 import하게 했다. 스타일 수정이 "여러 파일 뒤지며 30분"에서 "한 파일 2분"이 됐고, 전환 시 UI 불일치는 사라졌다.

**둘째, innerHTML은 XSS 표면이다.** react-markdown이 해주던 방어를 이제 직접 해야 한다. Marked 커스텀 렌더러에서 사용자 유래 텍스트가 HTML로 들어가는 모든 자리에 escape를 통일해서 적용했다.

**셋째, 커스텀 태그의 이중 처리.** 응답에는 출처 인용 칩이나 연관 질문 블록 같은 커스텀 태그가 섞여 온다. 완료 후에는 rehype-raw의 passThrough로 React 컴포넌트가 받아 클릭 이벤트까지 처리하지만, 스트리밍 중에는 컴포넌트가 없으니 전처리 단계에서 정적 HTML로 바로 변환한다. 여기서 부수 효과로 오래된 버그도 하나 잡혔다. 태그가 반쯤만 도착한 상태에서 일반 텍스트로 해석돼 코드 블록으로 보였다가, 닫는 태그가 오면 원래 모습으로 바뀌는 깜빡임이 있었는데, 태그 도착 즉시 HTML로 바꾸는 방식이 되면서 자연스럽게 사라졌다.

## 전처리도 단일 패스로: 84%

렌더러를 갈아끼우고 프로파일을 다시 떠보니, 이번엔 파서 앞단의 전처리가 눈에 들어왔다. 유니코드 정규화(전각 문자, 스마트 인용부호, 제어 문자 정리)가 **56개의 replace 체인으로** 텍스트를 56번 순회하고 있었고, 인용 링크 그룹화는 중첩 루프로 최악 O(n²), 커스텀 태그 변환이 6번 더 순회. 합쳐서 텍스트 한 번 처리에 **64회 순회였다.** 스트리밍 중엔 이게 누적 텍스트 전체에 매번 돈다.

고치는 방법은 교과서적이었다. 56개 replace 체인은 문자→치환 Map과 통합 정규식 하나로 합쳐 **1회 순회로,** O(n²) 인용 파싱은 정규식 기반 선형 스캔으로, 태그 변환들은 한 함수로 묶었다. 순회 횟수는 64회에서 10회로, **84% 감소.** 10,000자를 10회에 걸쳐 스트리밍하는 시나리오 기준으로 약 352만 연산이 55만 연산으로 줄어드는 계산이다.

## 실측: 20 FPS에서 55 FPS로

2,000자 분량에 코드 블록 5개, 표 2개가 포함된 문서를 약 15초간 스트리밍하며 Chrome DevTools로 측정했다.

![개선 후 성능 모니터](/images/recap/2025/flowai-cpu-sample2.png)
_개선 후 같은 조건에서의 성능 모니터. 스트리밍 중에도 CPU가 30% 안팎에 머문다._

| 지표 | Before (react-markdown 직행) | After (하이브리드) |
| --- | --- | --- |
| 평균 CPU | 70~90% | **30~40%** |
| 프레임 | 20~30 FPS, 드롭 빈번 | **55~60 FPS, 드롭 거의 없음** |
| 입력 응답 지연 | 200~300ms | 50~80ms |
| 스트리밍 중 메모리 증가 | +150MB | +30MB |

프로파일의 표정도 달라졌다. Before에는 Scripting 72%에 Idle 2%였던 Main 스레드가, After에는 Scripting 28%에 **Idle 52%가** 됐다. call tree 상위를 차지하던 VDOM diffing과 플러그인 체인이 사라지고, marked.parse와 innerHTML 갱신만 남았다. 스트리밍 중에 브라우저가 절반 넘게 놀고 있다는 뜻이고, 그만큼이 스크롤과 입력에 쓸 여유다.

돌아보면 이번 작업의 교훈은 기술보다 태도에 가깝다. React는 훌륭한 도구지만 모든 문제의 해결책은 아니었다. 초당 십수 회씩 자라는 텍스트를 그리는 일에는 선언적 UI의 비용이 이득을 넘어섰고, 그 구간만 정직하게 네이티브 DOM API로 우회하되 끝나면 다시 React에게 돌려주는 것, 즉 프레임워크의 한계를 인정하고 공존하는 설계가 답이었다.

## 다음 편: 같은 파이프의 반대쪽 끝

프론트는 이제 조용하다. 그런데 이 SSE 파이프에는 반대쪽 끝이 있다. 사용자가 응답 도중 탭을 닫거나 중지 버튼을 누르면, 서버는 그 사실을 언제 알까? 모른 채로 계속 토큰을 생성하고 있다면 그 비용은 누가 내고 있을까. 다음 편은 같은 파이프의 백엔드 쪽, 끊긴 연결을 서버가 감지하는 문제를 다룬다.
