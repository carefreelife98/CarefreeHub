## 실행기는 도는데, 이벤트는 누가 받는가

1편에서 예고한 대로, 빌더의 첫 번째 깊은 설계 결정은 노드도 그래프도 아니었다. **실행 이벤트를 누구에게 어떻게 전달할 것인가.**

실행기의 핵심 책임은 명확하다. 사용자가 그린 DAG를 LangGraph 런타임으로 실행하고 상태를 누적하고 DB에 남긴다. 그런데 실행기는 부산물로 이벤트를 뿜는다. 어떤 노드가 시작됐고 무엇을 출력했고 언제 끝났는지. 채팅에서 워크플로우를 호출하면 이 이벤트가 SSE로 프론트에 실시간 중계되어야 한다. 캔버스 위 노드들이 차례로 반짝이는 그 화면이 전부 이 이벤트로 만들어진다.

첫 구현은 자연스럽게 RxJS였다. NestJS 백엔드에서 이벤트 스트림이라면 반사적으로 나오는 선택이다.

```ts
// Before: 출력 채널이 실행기 시그니처에 박혀 있다 (개념 코드)
run(input): { runId: string; eventStream: Observable<WorkflowEvent> }
```

문제는 소비자가 하나가 아니라는 것이었다. 실행기를 부르는 경로는 세 곳인데, 이벤트 스트림이 필요한 곳은 하나뿐이다.

| 소비자 | 이벤트 스트림 |
| --- | --- |
| 채팅에서 워크플로우 호출 | 필요. SSE로 프론트에 실시간 전송 |
| 관리자 수동 실행 트리거 | 불필요. runId만 받고 즉시 응답 |
| 스케줄러 실행 (예정) | 불필요. fire-and-forget |

이 비대칭을 설계 입력에 넣지 않은 채 "어떤 RxJS 프리미티브를 쓸 것인가"만 고민한 것이 이후 모든 우회의 근원이었다. 프리미티브를 세 번 갈아탔고 네 번째에 RxJS 자체를 실행기에서 걷어냈다. 그 진화 과정을 순서대로 짚는다.

## 1차 Subject: 이벤트가 사라진다

처음엔 일반 `Subject`였다. 실행을 즉시 시작하고 `asObservable()`을 반환한다. 트리거 경로는 이걸로 충분하다. 구독하지 않아도 실행되니까.

채팅 경로가 깨졌다. `Subject`는 재생(replay)을 하지 않는다. 실행기가 스트림을 반환한 뒤 채팅 서비스가 `.subscribe()`를 붙이기까지는 몇 줄의 코드, 그러나 시간으로는 열려 있는 갭이다. 첫 노드가 그 사이에 빨리 끝나버리면 완료 이벤트가 허공에 발행되고 구독자는 영원히 오지 않을 terminal을 기다린다. 소비 측 Promise가 영영 해소되지 않고 **SSE 커넥션이 그대로 누수된다.** 늦게 온 구독자는 이미 지나간 방송을 들을 수 없다. 전형적인 late-subscriber race다.

## 2차 cold Observable: 이번엔 실행이 사라진다

그래서 cold Observable로 바꿨다. 구독하는 순간 실행이 시작되니 구독 전에 이벤트가 발행될 수 없다. race는 정의상 불가능해진다.

채팅은 고쳐졌고, 트리거가 죽었다. cold는 **구독이 없으면 실행 자체를 하지 않는다.** 트리거 경로는 runId만 받고 스트림을 구독하지 않으므로 워크플로우는 시작조차 되지 않는다. 실행 이력 row는 RUNNING 상태의 고아로 남고 실행 중 목록 맵에는 지워지지 않는 항목이 쌓인다. 이 건은 코드 리뷰를 돌린 독립 리뷰 에이전트 두 곳이 각각 프로덕션 블로커로 짚어냈다. 한쪽 소비자를 고치면 다른 쪽이 깨지는 구조. 이쯤에서 눈치챘어야 했는데, 한 번 더 프리미티브로 우회했다.

## 3차 ReplaySubject: 버그는 없지만 정직하지 않다

`ReplaySubject`는 두 요구를 모두 만족한다. 즉시 실행하니 트리거가 살고 버퍼가 늦은 구독자에게 지나간 이벤트와 terminal까지 재생해 주니 채팅도 산다. 실제로 이 상태는 버그 없이 동작했다.

메모리 우려도 검증해 봤다. 버퍼 크기는 동시 실행 중인 run 수 × 노드 수에만 비례하고, 버퍼 자체는 run이 끝나면 `complete()`와 맵 정리로 GC 대상이 된다. 진짜 메모리 리스크는 오히려 동시 실행 수 상한의 부재였고 이건 콜백으로 바꿔도 해결되지 않는 별개 과제라 백로그로 분리했다.

그런데도 찜찜함이 남았다. ReplaySubject는 **race가 발생할 수 있는 구조를 그대로 둔 채 버퍼로 그 틈을 메우는 미봉책이다.** 그리고 더 근본적으로, 출력 채널이 여전히 실행기 시그니처에 박혀 있었다. 이벤트가 필요 없는 소비자조차 Observable을 받아서 버려야 했다. 실행 엔진이 "내 이벤트는 RxJS 스트림으로 나간다"는 전송 방식을 알고 있는 것 자체가 관심사 누수였다.

## 결정: 이벤트는 콜백으로, 종료는 Promise로

그래서 네 번째는 프리미티브 교체가 아니라 구조 전환이었다. 실행 코어에서 RxJS를 제거하고 이벤트를 호출자가 넘긴 콜백에 위임한다.

```ts
// After: 실행 코어는 콜백만 안다 (개념 코드)
start(input, { onEvent, signal }): { runId: string; done: Promise<RunResult> }

// 채팅: 이벤트를 SSE로 흘리고 종료까지 대기
await runner.start(input, { onEvent: (e) => sse.send(e), signal }).done;

// 트리거: 빈 콜백, runId만 받고 즉시 응답
const { runId, done } = runner.start(input, { onEvent: () => {} });
void done.catch(() => {});
return { runId };
```

설계의 요점은 세 가지다.

**첫째, 두 소비자의 차이를 반환 구조로 표현했다.** runId는 실행 이력 생성 직후 동기적으로 확정되므로 트리거는 `done`을 기다리지 않고 즉시 응답할 수 있다. 채팅은 `await done`으로 종료까지 대기한다. fire-and-forget과 스트리밍 대기가 API 하나에서 자연스럽게 갈라진다. "출력이 필요 없다"는 요구도 빈 콜백 `() => {}`로 그대로 표현된다. Observable을 구독해서 버리던 3차의 어색함과 비교하면 의도가 코드에 정직하게 드러난다.

**둘째, terminal의 의미를 Promise 의미론에 맞췄다.** 성공과 중단(사용자 stop, 연결 해제)은 `done` resolve, 실패만 reject다. 중단은 에러가 아니라는 판단 덕에, 사용자가 stop을 눌러도 채팅의 `await done`이 매달리지 않고 풀린다.

**셋째, race를 막은 게 아니라 없앴다.** 별도의 스트림 객체가 존재하지 않으니 "반환과 구독 사이"라는 갭 자체가 소멸한다. late-subscriber race도, 그것을 메우던 ReplaySubject 버퍼도 함께 불필요해진다. 의존성 방향도 바로잡혔다. 저수준인 실행 코어가 고수준인 전송 방식(RxJS, SSE)을 모르게 됐고 RxJS는 그것이 진짜 필요한 채팅 어댑터 한 곳에만 남았다.

솔직하게 적어두면, 이 전환이 만장일치는 아니었다. 독립 리뷰 에이전트는 ReplaySubject 유지를 권고했다. 이미 테스트된 실행 경로를 갈아엎는 리스크가 관심사 분리라는 이득보다 크다는 논리였고 출시 이후였다면 맞는 말이다. 하지만 당시는 서비스 출시 전, "처음부터 다시"를 적용할 수 있는 드문 타이밍이었다. 이상적 설계를 택했고 실행기와 채팅 스위트 255개 테스트를 콜백 기반으로 재작성하는 비용을 치렀다.

## 스트리밍 시리즈와 같은 결론에 닿다

흥미로운 건, 전혀 다른 문제를 다룬 [스트리밍 성능 시리즈 3편](/posts/flow-ai/streaming-03-abort)이 같은 교훈에 닿았다는 점이다. 거기서는 NestJS 인터셉터들이 연결 종료 이벤트를 서로 먼저 들으려 경쟁하다 로깅이 깨졌고 해법은 "상태를 먼저 아는 레이어가 확정 후 콜백으로 위임하라"였다. 이번 편의 결론도 결국 같다. **여러 소비자가 하나의 이벤트 소스를 두고 경쟁한다면, 구독 모델을 정교하게 만들기보다 명시적 콜백으로 순서와 책임을 코드에 박는 편이 낫다.** 두 사건 이후, "이벤트를 누가 언제 듣는가"가 암묵적인 설계는 반사적으로 의심하게 됐다.

## 배운 것

1. **소비자 목록이 설계 입력이다.** 구독하지 않는 소비자가 존재한다는 사실을 처음부터 명시했다면 1\~3차 우회는 없었다. 채팅 하나만 보고 시그니처를 정한 것이 세 번의 교체를 불렀다.
2. **버퍼는 race의 해법이 아니라 은폐다.** ReplaySubject는 동작했지만 문제가 생길 수 있는 구조를 남긴 채 증상만 가렸다. 구조를 바꿀 수 있는 시점이라면 방어보다 제거가 맞다.
3. **상위 계층의 도구가 반환 타입에 새어 나오면 관심사 누수다.** 실행 엔진이 Observable을 반환하는 순간 엔진은 전송 방식에 결합된다. 콜백은 가장 낮은 공통분모라 어떤 전송 방식과도 결합하지 않는다.
4. **같은 리팩터링도 타이밍이 결론을 바꾼다.** 출시 후라면 ReplaySubject 유지가 정답이었을 것이다. 이상적 설계로 갈아탈 수 있는 기간은 생각보다 짧다.

덧붙여 하나. 중단 신호(AbortSignal)는 그래프 컴파일 시점이 아니라 실행 시점에 주입해야 한다. 컴파일된 그래프는 캐시되어 재사용되므로 signal을 컴파일 클로저에 박으면 이전 실행의 낡은 signal이 살아남는다. 이번 리팩터링 중에 밟을 뻔한 지뢰라 기록해 둔다.

실행은 안정됐다. 다음 질문은 사람이었다. 누가 이 워크플로우를 보고 고치고 실행할 수 있는가. 권한 모델을 백지에서 다시 그린 ADR이 다음 편이다.
