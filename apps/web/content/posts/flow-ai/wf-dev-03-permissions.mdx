## 누가 이 워크플로우를 보고, 고치고, 실행할 수 있는가

2편은 이 질문으로 끝났다. 이벤트가 흐르고 그래프가 돌기 시작하자 다음 문제는 기계가 아니라 사람이었다. **누가 만들었고, 누구에게 보이고, 어디에서 쓰이는가.**

처음에는 이 질문이 없었다. 빌더는 "내가 만든 워크플로우를 내가 실행하는" 도구였으니까. 그런데 AI 비서의 예약 실행에 워크플로우를 붙이는 순간 판이 커졌다. 플랫폼이 제공하는 추천 워크플로우(아침 브리핑, 일정 준비 등)와 사용자가 직접 만든 워크플로우가 한 모달에 섞여야 했다.

급한 대로 임시 모델을 만들었다. `scope(SYSTEM | USER)` 곱하기 `category(SECRETARY | CUSTOM)`의 4사분면. 비서 모달, 빌더 게이트, 백엔드 가드까지 다 붙였고 실제로 돌아갔다. 단일 도메인만 보면 문제가 없었다.

문제는 요구사항이 하나 더 도착했을 때 드러났다. **"회사 어드민이 자기 회사 사용자들이 쓸 공통 워크플로우를 만들고 켜고 끌 수 있어야 한다."** 이 문장을 임시 모델에 넣을 자리가 없었다. SYSTEM은 전체 사용자용이고 USER는 본인용이다. "회사 단위"라는 중간 격리가 통째로 누락돼 있었다.

자리만 없는 게 아니었다. `scope`라는 단어가 권한 경계와 격리 범위 두 의미를 한꺼번에 담고 있어서 값 하나를 추가하려는 순간 리뷰마다 "어느 scope의 SYSTEM?"을 되물어야 했다. 소유권과 가시성이 자연스럽게 1:1인데 두 축으로 억지로 찢어놓으니 유효한 조합과 잘못된 조합의 매트릭스만 복잡해졌다. 땜질 대신 갈아엎기로 했다.

## 백지 재설계: 두 개의 직교 축

요구사항을 다시 세 줄로 적었다.

1. 플랫폼 운영자는 백오피스에서 모든 사용자가 쓸 공통 워크플로우를 관리한다.
2. 각 회사 어드민은 자기 회사 사용자가 쓸 공통 워크플로우를 관리한다.
3. 모든 사용자는 자기에게 보이는 공통 워크플로우와 본인이 만든 워크플로우를 쓴다.

세 줄을 관통하는 질문은 두 개뿐이었다. **누가 만들어서 누구에게 보이는가(소유권), 그리고 어디에 노출되는가(쓰임새).** 이 둘은 서로 직교한다. 임시 모델의 실패는 이 두 질문을 한 단어에 욱여넣은 데서 왔다.

후보는 셋이었다.

- **A. 소유권 단일 enum:** `PERSONAL | COMPANY | GLOBAL` 하나로 끝. 단순하지만 "사용자가 만든 워크플로우를 회사 동료에게 공유"하는 미래 케이스를 영영 표현할 수 없다. 소유와 가시성이 한 축에 묶여 분리가 불가능하다.
- **B. creatorScope 곱하기 visibility:** 공유 케이스까지 표현 가능. 대신 유효한 조합 5개에 잘못된 조합 4개가 따라온다. enum만으로는 잘못된 조합을 못 막아 가드 함수가 필수. 지금 범위엔 과설계다.
- **C. creatorScope 곱하기 purpose:** 소유권과 가시성은 1:1로 묶고(`USER | COMPANY | PLATFORM`), 노출처만 별도 축으로(`GENERAL | SECRETARY`).

선택은 **C였다.** 세 요구사항이 완전히 표현되고 잘못된 조합이 구조적으로 생기지 않는다. B가 열어주는 공유 케이스는 "회사 어드민이 COMPANY로 격상 등록"하는 흐름으로 흡수했다. 정말 실수요가 오면 visibility 컬럼 하나를 추가해 비파괴로 확장하기로 적어뒀다. 미래를 미리 짓지 않되, 막지도 않는 선택이다.

이 모델의 힘은 가시성 쿼리가 **OR 절 하나로 끝난다는 것**이다.

```ts
where: {
  isActive: true,
  OR: [
    { creatorScope: 'PLATFORM' },
    { creatorScope: 'COMPANY', companyId: myCompanyId },
    { creatorScope: 'USER', creatorId: myUserId },
  ],
}
```

임시 모델에서 세 그룹을 각각 불러 합치던 비서 모달 호출도 단일 조건 호출로 줄었다. 권한 경계가 데이터 모델 안에 선언적으로 들어가 있으면 코드는 그걸 읽기만 하면 된다.

가드는 축과 1:1로 붙였다. 컨트롤러를 진입 surface별로 셋으로 쪼개고 각 컨트롤러가 자기 scope만 책임진다.

| creatorScope | 만드는 사람 | 보이는 범위 | 진입 surface |
| --- | --- | --- | --- |
| USER | 사용자 본인 | 본인만 | 빌더 |
| COMPANY | 회사 어드민 | 같은 회사 전원 | 어드민 콘솔 |
| PLATFORM | 플랫폼 운영자 | 전체 사용자 | 백오피스 |

요청 body의 scope가 컨트롤러의 책임 scope와 다르면 400. 실수가 런타임 깊숙한 곳이 아니라 진입 지점에서, 컴파일에 가까운 시점에 잡힌다. 두 어드민 컨트롤러의 코드가 80% 겹치는 건 의도된 중복으로 남겼다. 세 번째가 생기면 그때 추출한다.

마이그레이션은 가장 과감한 결정이었다. 기존 워크플로우 데이터를 **전부 지우고 백지에서 시작하기로 합의했다.** 아직 초기 단계라 지불할 수 있는 비용이었고 낡은 모델의 데이터를 새 모델로 끌고 오는 backfill 비용과 맞바꿨다. 이 타이밍을 놓치면 다시는 못 하는 종류의 결정이다.

## 권한이 화면이 되다

모델을 갈아엎고 닷새 뒤, 이번엔 메인 페이지를 갈아엎었다. 우연이 아니었다.

기존 홈은 한 파일에 카드, 그리드, 빈 상태, 페이지가 다 들어있는 "내 것 / 추천" 2구분이었다. 회사 워크플로우가 "내 것"에 섞여 들어오면서 소유와 권한의 의미가 화면에서 흐려졌다. 정보구조, 디자인, 코드 구조 전부가 불만이었는데 재설계를 시작하니 분류축이 고민거리가 아니었다. **creatorScope 그대로였다.** 내 것(USER), 회사(COMPANY), 추천(PLATFORM)의 3구분 세로 스택. 대신 위계는 차등을 뒀다. 내 것은 주역이라 풀 액션과 교육형 빈 상태를 주고 회사와 추천은 보조라 읽기 전용에 빈 그룹은 숨겼다. 카드는 한 종류로 통일하고 차이는 액션 구성과 밀도로만 냈다.

권한 모델이 정리되기 전이었다면 이 화면은 그릴 수 없었다. "이 섹션에 뭐가 오는가"라는 질문의 답이 곧 가시성 OR 절의 세 줄이니까.

이틀 뒤 한 번 더 진화했다. 워크플로우가 단순 목록을 넘어 연동 관리, 실행 기록, 템플릿 갤러리까지 갖는 작은 제품이 되면서 3구분 홈을 **홈 / 연동 / 기록 / 템플릿의 4탭 허브**로 넓혔다. 추천(PLATFORM) 섹션은 템플릿 탭으로 승격됐다. 3구분 시절 "목록 DTO에 실행 이력도 횟수도 없어 카드에 보여줄 게 없다"던 제약은 이번엔 API를 확장해 정면으로 풀었다. 어느 서비스에 연결되는지, 몇 번 돌았는지, 수동인지 예약인지까지 카드가 말할 수 있게 됐다.

돌아보면 순서가 중요했다. 모델 재설계, 3구분, 4탭이 8일 안에 연달아 일어났는데 역순이었다면 성립하지 않았다. **내비게이션이 정리된 게 아니라 모델이 정리되니 내비게이션이 따라온 것이다.**

## 권한 모델은 데이터 모델이자 정보 구조다

이번 사이클에서 남은 통찰은 하나로 수렴한다. 권한 모델은 접근 제어 규칙 목록이 아니다. **"누가 만들고 누구에게 보이는가"라는 도메인의 구조 그 자체다. 그 구조는 쿼리가 되고 가드가 되고 결국 화면이 된다.** 축이 직교하면 가시성은 OR 절 하나가 되고, 컨트롤러는 세 개의 깔끔한 surface가 되고, 메인 페이지는 세 개의 섹션이 된다. 축이 엉켜 있으면 그 반대의 일이 모든 레이어에서 일어난다.

하나 더. 단어 하나의 과적은 생각보다 비싸다. `scope`가 두 의미를 담는 순간부터 모든 대화에 되묻기 비용이 붙었다. 이름을 나누는 것(creatorScope, purpose)만으로 리뷰의 절반이 사라졌다.

판이 정리되자 남은 것은 지능이었다. 자연어 한 줄로 워크플로우를 그려주는 Planner. 반복문 하나로 시작한 그 물건을 다섯 노드짜리 그래프로 다시 지은 이야기가 다음 편이다.
